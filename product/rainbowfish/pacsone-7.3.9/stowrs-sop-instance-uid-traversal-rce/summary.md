# PacsOne Server 7.3.9 - Path Traversal in the DICOMweb STOW-RS Store Path (CWE-22)

Advisory: https://0day-rubbish.com/blog/rainbowfish-pacsone-stowrs-sop-instance-uid-traversal-rce
Repository: https://github.com/Exploit-Garbage/0day-Rubbish
Contact: disclosure@0day-rubbish.com

Author: 0day Rubbish Research Team

## Summary

PacsOne Server is a closed-source commercial PACS (medical imaging archive and DICOM server) from RainbowFish Software, California, United States; it combines a native C++ DICOM/HL7 service with a PHP web interface of 204 endpoints over MySQL and Apache, fronted by one Apache alias mapping `/pacsone` to the product's `php/` directory. Its DICOMweb STOW-RS handler `stowrs.php` reads the SOP Instance UID attribute `(0008,0018)` out of the posted DICOM object and uses it as the storage filename: `import()` in `dicomweb.php` (approximately lines 1391-1440) computes `$newfile = $dir . "/" . $uid` and calls `rename($tempfile, $newfile)` with no character validation, no canonicalisation and no containment check, so a UID of `../../../php/x.php` moves the received object out of the study directory and into the directory Apache serves. Because the DICOM Part 10 preamble is never interpreted by the DICOM parser, it can carry `<?php system($_GET["c"]); ?>`, and once the file is in the served tree the PHP module executes it under the web server identity. We verified the full chain over HTTP and reached `uid=33(www-data)` on a medical imaging server, confirmed with `id`, `whoami`, a read of `/etc/passwd`, a marker write-and-read under `/tmp`, `hostname` and `uname`. The endpoint is authenticated: reaching it requires a credential for an account that passes `hasaccess("stowrs", $username)`, which on the tested installation was the installer-created administrator account; there are no default web credentials, and we make no claim of unauthenticated reachability. The practical significance is that a privilege intended to mean "may store DICOM images" becomes "may execute arbitrary code on the host holding the patient image repository".

- Component: DICOMweb STOW-RS store path — `stowrs.php` (entry), `DicomWebStow::__construct` in `dicomweb.php:1165` (multipart capture and `tempnam()` staging), `store()` in `dicomweb.php:1592`, and `import()` in `dicomweb.php:1391-1440` (sink).
- Sink and source: the sink is `rename($tempfile, $dir . "/" . $uid)` in `import()`; the source is DICOM tag `(0008,0018)` in the posted `application/dicom` part, read back by `RawTags::getAttr()` (`dicom.php:4516`), which returns the raw attribute value; the Explicit VR parser `parseDataExplicit()` (`dicom.php:4378`) applies `trim()` only. The store directory comes from `getStowRsStoreDir()` (`database.php:1780`) = archive directory + `stowrs/` + a per-day directory from `date("Y-m-d-D")`.
- Sanitization: none on this path. The product does contain a UID validator, `isUidValid()`, and does apply it on the unauthenticated `wadoAnonymized.php` read path, where its character whitelist blocks `/`; the store path that turns a UID into a filename never calls it. That asymmetry — a validator that exists, applied to a read path and omitted on the write path — is the root cause.
- Ordering caveat that decides whether a reproduction works: the `rename()` happens before the database inserts, and any failed insert into `image`, `series`, `study` or `patient` triggers `unlink($newfile)`. A minimal DICOM object therefore writes the payload and then deletes it (HTTP 409, failure reason 272 `ProcessingFailure`). Making all four inserts succeed — which requires Patient Name `(0010,0010)`, Patient ID `(0010,0020)` and the pixel attributes `(0028,xxxx)` — keeps the file. Any attempt to reproduce this without those attributes will look like a false positive.

## CVSS Score

- Score: 7.2 High (`CVSS:3.1/AV:N/AC:L/PR:H/UI:N/S:U/C:H/I:H/A:H`) — authenticated arbitrary file write into the served directory, escalating a DICOM store privilege to code execution as the web server identity on a PACS host that holds the patient imaging repository.
- Attack Vector Network: the endpoint is an HTTP service behind the same Apache alias as the management console; our requests crossed into the container's published port over HTTP.
- Attack Complexity Low: no race, no memory-layout or cryptographic dependency. The only deployment-variable quantity, the number of `../` components between the study directory and a served directory, is discoverable because the STOW-RS response echoes the UID back in `(0008,1155)` and distinguishes success (HTTP 200) from failure (HTTP 409, reason 272).
- Privileges Required High: only the administrator-group account passed the gate. `isAdministrator()` short-circuits all privileges for that group, and the `privilege` table on the tested installation contained a single row with `stowrs=1`. No lower-privileged role was demonstrated or documented to hold `stowrs`.
- User Interaction None: one authenticated POST followed by one GET.
- Confidentiality / Integrity / Availability all High: `www-data` owns the study repository and can read the configuration holding database credentials (C); it can alter, delete or fabricate stored studies and replace product code (I); and the same write access reaches the files the imaging service depends on (A).
- Scope: Unchanged. The PHP interpreter that executes the payload is part of the same product serving the vulnerable endpoint, on the same host, under the same service identity, and our traversal target was inside the product's own served directory. No second component with an independent authorization boundary was crossed, and no cross-account or cross-machine outcome was demonstrated.
- CWE: primary CWE-22 (Improper Limitation of a Pathname to a Restricted Directory); contributing CWE-73 (External Control of File Name or Path) and CWE-20 (Improper Input Validation). CWE-434 and CWE-94 describe the outcome rather than the defect and were rejected.
- Recorded-score note: no numeric CVSS value accompanied the verification evidence we gathered for this finding (that evidence recorded its type, authentication requirement and achieved identity), so 7.2 is derived here from the vector with the CVSS 3.1 formula — ISS 0.914816, Impact 5.873119, Exploitability 1.234708, unrounded base 7.107826 — rather than copied from a recorded figure. There is no recorded-versus-computed discrepancy to correct.
- Conditional reading, labelled as conditional: in a deployment that grants `stowrs` to a non-administrator account (an acquisition device, a partner PACS, an imaging application service account), the least privileged principal reaching the sink is a low-privileged user, and the honest rating for that deployment is 8.8 High (`CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H`, unrounded 8.708373). We did not demonstrate that any non-administrator account can be granted `stowrs` through the product, so this is not the headline score; one query against the `privilege` table tells an operator which reading applies.
- Rejected readings, published for transparency: `S:C` would compute to 9.1 (`CVSS:3.1/AV:N/AC:L/PR:H/UI:N/S:C/C:H/I:H/A:H`, unrounded 9.087684) and is rejected for the Scope reasons above; `AC:H` would compute to 6.6 (`CVSS:3.1/AV:N/AC:H/PR:H/UI:N/S:U/C:H/I:H/A:H`, unrounded 6.578666) and is rejected because the depth unknown carries observable feedback and costs one request per guess. We also publish no `PR:N` vector: no unauthenticated path to this sink exists, and the bypass-file branch (`$STOWRS_BYPASS_FILE`, fixed `wado` credentials when its file exists) is dead code on a default installation because that file does not exist.

## Affected Products

- PacsOne Server (PACS Server In One Box), Premium Edition, version 7.3.9, Linux x86-64 distribution, from RainbowFish Software (California, United States). Closed-source commercial PACS medical imaging server.
- Affected component: the DICOMweb STOW-RS store path — `stowrs.php` and `import()` in `dicomweb.php` (approximately lines 1391-1440), with the underlying validation gap in `RawTags::getAttr()` (`dicom.php:4516`) and `parseDataExplicit()` (`dicom.php:4378`).
- Runtime stack as tested: Ubuntu 24.04 (x86-64) container, Apache 2.4.58 with `mod_php`, PHP 8.3, MySQL 8.0 (`default_authentication_plugin=mysql_native_password`, required by the vendor's bundled MariaDB client library), installed with the vendor's `install.sh` and native `Setup.exe`; installation root `/opt/pacsone`, archive directory `/opt/pacsone/archive/`, web entry point the Apache alias `/pacsone`.
- Only version 7.3.9 on Linux x86-64 was tested. No other 7.x point release, no other edition, and not the Windows distribution (`Premium-7.3.9-x64.exe` was obtained but never deployed) is claimed affected. The defect is in shipped PHP source, so other builds sharing that store path are expected to behave identically, but we did not test them and do not assert it.
- Verification method and its boundary: the chain was driven end to end over HTTP against the vendor-installed instance — authentication, `multipart/related; type=application/dicom` POST, JSON response, and execution of the written file — and confirmed by inspecting the written file (owner, size, mode) and the four database rows inside the container. Three properties of the instance were established by us, not shipped as defaults: the database name, account and password, and the application administrator account and password, were all chosen at the `Setup.exe` prompts (the product ships no default web or database credentials), and the archive and `php` directory ownership had to be restored with `chown -R www-data:www-data` to match the installer's own permission model. Traversal depth (three `../` components) is specific to that archive layout. The native DICOM/HL7 protocol layer is not assessed: its server processes were defunct on our instance, with no listener on the DICOM ports.
- Privilege ceiling: `uid=33(www-data)`, the Apache worker identity. Root was not reached, no privilege escalation was attempted, no container or host escape was attempted, and no other machine was contacted. The directory and title of this advisory claim no more than that identity.

## Impact

- Confidentiality in clinical terms: `www-data` is the identity that owns the DICOM study repository, so code execution there permits reading stored studies — and a DICOM object carries patient name, patient ID, accession number, birth date, sex, referring physician, institution and equipment details alongside the pixels. Reading the archive means reading that data for every stored study. We confirmed read access as a capability proof (`/etc/passwd`) and did not enumerate or copy study data.
- The same identity reads the product's PHP configuration, which holds the installer-configured database credentials, and with them the full relational schema: patient, study, series and image records, user accounts, and the `privilege` table itself.
- Integrity in clinical terms: the write access permits altering pixel data in stored instances, substituting or deleting studies, and introducing fabricated ones. The demonstrated chain already performs a small version of that as a side effect — a successful store inserts patient, study, series and image rows — which is why our PoC uses obviously synthetic identifiers and warns before it runs. Fabricated or altered imaging is a patient-safety issue: a reader has no independent way to detect post-acquisition modification.
- A further destructive primitive follows from the code, argued from `rename()`'s atomic replace semantics and not exercised by us: the failure branch's `unlink($newfile)` operates on the same attacker-chosen path, so a deliberately failing store can replace and then remove an existing file that the web server user can write. Our PoC refuses to target any path that already resolves, for exactly this reason.
- Availability: the written script runs inside the Apache worker context, so worker processes can be consumed and the files the imaging service depends on can be corrupted or removed, interrupting the study browser and the DICOMweb services. Removal or corruption of stored instances is likewise an availability event for downstream consumers of the archive. No denial-of-service test was performed.
- Persistence: the chain does not install persistence itself, but the file it leaves in the served PHP directory persists until removed and is then executable by any unauthenticated HTTP client that can reach the alias — the store gate does not protect what the store created. Rotating the credential does not remove it, and its use does not appear in STOW-RS logs.
- Network position: DICOMweb STOW-RS exists to be called by modalities, worklists and partner archives. In a deployment that follows that design, an acquisition-side credential becomes a code-execution credential on the imaging host. We did not survey public exposure and make no claim about how many installations are internet-facing; we do note that the product provides no internal separation between console exposure and store-interface exposure, since one Apache alias fronts both.
- Detection: a successful traversal leaves an `image.path` row containing `../` (on our instance `/opt/pacsone/archive/stowrs/<day-dir>/../../../php/x.php`), a mode `0600` file owned by the web server user in the served PHP tree, an access-log pattern of a POST to `stowrs.php` followed by GETs to a previously nonexistent `.php` path, and synthetic patient/study/series rows. It leaves nothing in DICOM upper-layer logs and generates no privilege-change or egress event.
- Not claimed: hospital-wide or network-wide compromise. The blast radius demonstrated is the imaging server and everything stored on it, under one service identity.

## Mitigation

1. Validate the SOP Instance UID against the DICOM UID grammar before it is used for anything: in `import()` (`dicomweb.php` approx. lines 1391-1440), reject the store unless `getAttr(0x00080018)` matches `^(0|[1-9][0-9]*)(\.(0|[1-9][0-9]*))*$` with total length at most 64 and alphabet `[0-9.]` only. The product already contains `isUidValid()` and already calls it on the `wadoAnonymized.php` read path; calling it here closes the traversal at no interoperability cost, since every conforming peer sends UIDs made only of digits and dots.
2. Stop deriving filesystem paths from protocol identifiers. Generate the storage name server-side (a random or content-derived token, optionally partitioned by date or study), keep the SOP Instance UID as a database column, and resolve objects through the database. Apply the same treatment to Study and Series Instance UIDs wherever either builds a directory name.
3. Enforce containment at the write, independently of validation: canonicalise the intended destination's parent with `realpath()`, compare against the canonical store root with a trailing separator, reject symlinks, and `basename()` any identifier used in a path — then only call `rename()`.
4. Move the write after the decision to keep the object, and never `unlink()` a path you did not validate. Stage the temporary file in a non-served directory, insert the rows in a transaction, and move the object to its final location only on commit; if a failure branch must delete something, let it delete the server-generated staged path.
5. Separate writable data from executable code in the deployment: keep the archive directory out of the served tree, disable script execution in every writable data directory (`php_admin_flag engine off` or an equivalent handler restriction, plus `open_basedir` where practical), and make the served PHP tree non-writable by the web server identity after verifying that no endpoint your installation uses writes there.
6. Validate identifiers on the parse path, not only at the sink: applying the UID grammar inside `parseDataExplicit()` (`dicom.php:4378`) for the `UI` VR protects every consumer of `getAttr()`, including future code that uses a UID in a path, a filename, a shell argument or a log format string.
7. Remove the latent authentication fallback and the unauthenticated adjunct endpoints: delete the `$STOWRS_BYPASS_FILE` branch and its fixed `wado` credentials; retire `setup.php` after installation (and quote its database name as an identifier rather than concatenating it into `create database` and `grant all privileges`); remove `phpinfo()` from `Hello.php`; restore a real authorization check on `risquery.php` whose referer check is commented out; and have `Setup.exe` generate a per-installation signup database credential instead of the hardcoded pair at `constants.php:580-581`.
8. Ship a regression test: send a STOW-RS object whose SOP Instance UID is `../../../<served-dir>/probe.php`, then assert the response is a rejection, that no file exists outside the study directory, and that no `image` row contains a `path` with `../`. The second assertion matters because the write precedes the record — a fix that only changes the response still moves bytes.
9. Operator-side until a patch exists: restrict `stowrs.php`, `wadors.php` and `qidors.php` at the proxy or firewall to the specific modality, worklist and partner addresses that legitimately store studies; audit `privilege` rows with `stowrs=1` and treat each such credential as equivalent to a shell on the imaging host (long, unique, secret-managed, rotated, per-device rather than shared, never the administrator account); segment the PACS from general clinical and corporate traffic and restrict its egress; monitor for new executable-suffix files in the served PHP tree and query the database periodically for `image.path LIKE '%../%'`; and if you find evidence the traversal was used, treat it as a confidentiality incident affecting the stored study repository and follow your obligations for protected health information.
