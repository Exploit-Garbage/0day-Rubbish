# D-Link DAP-2310B (DAP-2660 byte-identical merge) - atp ExeShell Dollar-Parentheses Command Injection Executing as Root

Advisory: https://0day-rubbish.com/blog/exeshell-command-injection-root-rce
Repository: https://github.com/Exploit-Garbage/0day-Rubbish
Contact: disclosure@0day-rubbish.com

## Summary

D-Link is a Taiwanese networking vendor whose business access-point line is deployed as interior wireless
infrastructure in small and mid-sized offices. The DAP-2310B is a Wireless N300 business access point with
an HTTP management interface; the firmware analyzed here is v3.00r048, a MIPS 32-bit big-endian build. The
management plane of that image is not a general-purpose web server. `sbin/httpd` - 228756 bytes, an
appweb-derived server carrying D-Link session and access templates - fronts a self-built template processor,
`sbin/atp`, of 51296 bytes: a stripped MIPS 32-bit MSB binary that implements a PHP-style instruction set
(query, set, get, anchor, fwrite, fread) and, among its builtins, one named `ExeShell` that runs a shell
command. `sbin/xgi` and `sbin/sgi` are symbolic links to that same binary, and the server's own configuration
template in `/etc/templates/httpd/httpd.php` maps the `.xgi` extension onto `/sbin/xgi`.

The defect is the `ExeShell` builtin at `0x405860`. It passes its argument to `fcn.00405690` at `0x405690`,
and if that validator returns a non-zero value it builds the format string `"%s > /dev/console"` (stored at
`0x409c80`) around the argument - nothing else, no quoting, no escaping, no argument vector - and hands the
result to `system()`, resolved through the GOT at `0x41ba2c` to `0x4085a0`. The second parse performed by
`/bin/sh -c` is the whole vulnerability: the argument is shell text, not data.

The validator is a blocklist over exactly three characters. It skips leading blanks, skips leading `;`, `&`
or `|`, then requires each segment to begin with the literal `submit` (a six-byte, case-sensitive
`strncmp`) and to be separated from the next segment only by `;`, `&` or `|`. Its charset sits at `0x409c40`
and was measured directly as the three bytes `3b 26 7c 00`, with the `submit` literal at `0x409c44`. The
validator never inspects `$`, `(`, `)` at all, and never inspects the backtick (`0x60`) or the newline
(`0x0a`). Because `$( )` is itself a complete command container, a value that begins with `submit` and
contains no separator can still carry an arbitrary command.

The value arrives at that validator already URL-decoded. The query parser `fcn.0040405c` splits the query
string on `&` and decodes each segment in place with `fcn.00401c90` at `0x401c90`, which turns `%XX` into the
literal byte, so an encoded `%24%28...%29` reaches both the validator and `system()` as literal `$(...)`. The
gate above it compares the parameter name with `strcasecmp(key, "ExeShell")` (GOT `0x41ba04` to `0x408610`),
so it is case-insensitive and a lowercase `exeshell=` reaches the same branch; three conditions then apply -
an `=` must be present in the examined segment, the page must not be `remotemainte.xgi`, and the value must not
contain the string `telnetd`. The request-level filter one level up blocks only when `%60` and `telnetd` appear
together. None of those conditions is an obstacle to `submit$(...)`.

The complete request is therefore one authenticated GET:
`GET /cfg_valid.xgi?exeshell=submit%24%28id%3e/tmp/marker%29`. `xgi_main` at `0x405304` reads `REQUEST_URI`
through `getenv` and passes it straight to the parser at `fcn.0040478c`; it never opens a template file, which
is why the `.xgi` path need not exist on disk - the www tree of both affected products contains no `.xgi` file
at all, and `cfg_valid` is a `.php` page. The extension alone routes the request. What the device executes is
`system("submit$(id>/tmp/marker) > /dev/console")`: the shell substitutes the command before the `submit` stub
runs, so `id>/tmp/marker` executes, the stub then fails as an unknown command, and the trailing redirection
applies only to that failing stub.

The authentication boundary is real and is stated as such. The `.xgi` extension requires a session
(`SessionControl On`, `SessionFilter { php xgi _int }`) and HTTP Basic credentials (`Realm`,
`UserFile /var/etc/httpasswd`, generated by `httpasswd.php` from the `rgdb` key `/sys/user`). The `atp`
binary itself contains no authentication check; the gate sits entirely in front of it, and the branch above
the sink only applies the value-shape conditions listed above. This is an authenticated finding, scored with
Privileges Required: High. The factory-default `admin`/`admin` pair read from `etc/config/defaultvalue.gz` is
disclosed separately as CWE-798 and is not the vector here: changing that password does not remove this
defect, because the defect consumes a legitimate administrator session.

Verification boundary, stated exactly: the dynamic evidence is a sink-level replication on an isolated
x86-64 Linux sandbox, not a live appliance. Emulating `sbin/atp` under `qemu-mips-static`, and emulating the
device's busybox `ash` the same way, both ended in `Bus error (core dumped)` - the recorded MIPS big-endian
qemu-user SIGBUS limitation - so no end-to-end device execution was performed and no HTTP request was fired at
hardware. The replication compiled a native program that reproduces the recorded construction
`snprintf(buf, sizeof(buf), "%s > /dev/console", s); system(buf);` and ran it as root inside that sandbox; the
marker file contained `uid=0(root) gid=0(root) groups=0(root)` and the benign control
`system("submit id > /dev/console")` created no marker. Root was observed in the replication environment only.
The device-side identity is the record's conclusion that `atp` runs as root because the httpd path performs no
setuid privilege drop, so `system()` inherits root context.

The DAP-2660 (AC1200 access point, firmware v2.00r140) is merged into this advisory at build-identity level.
Its `sbin/atp` is byte-identical to the DAP-2310B one, matching on both MD5
`32595db17de80bcedd798cca5b365ec6` and SHA256
`dc6cffbe41a7d9ab56a9d0d7168e20ec453ab12dc0dfbc5d3c1de931ca7178d2`, with `ExeShell` at `0x405860`, the
validator at `0x405690` and `xgi_main` at `0x405304` at the same offsets; `httpd.php` and `httpd_server.php`
are byte-identical as well, which fixes the `.xgi` route and the same authenticated boundary on both models.
One exploit URL and one fix address both.

- Component: the `ExeShell` builtin of the self-built `atp` template processor shipped as `sbin/atp`
  (51296-byte stripped MIPS 32-bit MSB binary, MD5 `32595db17de80bcedd798cca5b365ec6`), reached as
  `sbin/xgi` through the `.xgi` extension mapping in `/etc/templates/httpd/httpd.php` on DAP-2310B firmware
  v3.00r048 and on the byte-identical DAP-2660 firmware v2.00r140
- Sink: `system()` at `0x405860` on a buffer built by `sprintf(buf, "%s > /dev/console", s)` from the
  unsanitized argument, executing through `/bin/sh -c`
- Source: the value of the `exeshell` query parameter after in-place URL decoding by `fcn.00401c90`, matched
  case-insensitively against `ExeShell` at `0x404fbc`
- Sanitization: `fcn.00405690` at `0x405690` checks only the three separator bytes `;&|` and a `submit`
  prefix per segment; `$`, `(`, `)`, backtick and newline pass untouched
- Authentication: HTTP Basic administrator session plus the `.xgi` session predicate; the `atp` layer
  performs no authentication of its own

## CVSS Score

- Score: 7.2 High (`CVSS:3.1/AV:N/AC:L/PR:H/UI:N/S:U/C:H/I:H/A:H`) - an administrator credential holder
  converts an intended management request into arbitrary command execution on the access point, in the root
  context the record attributes to `atp`
- Attack Vector: Network - the injection point is the HTTP management interface of the device, an IP service
  whose reachability in a given deployment is a configuration property (management VLAN, port forward, or a
  position already inside the local network); the research record does not bound the plane to a link-local bus
  and does not measure wide-area exposure of an unmodified deployment
- Attack Complexity: Low - a single correctly encoded authenticated GET is the whole detonation, with no race,
  no timing window, no state machine and no memory-corruption groom
- Privileges Required: High - the request must carry a valid administrator session and Basic credential; the
  `atp` layer itself holds no account model, and the record documents no lower-privilege web tier that reaches
  the `.xgi` route
- User Interaction: None - the credential holder drives the request directly; no victim action is involved
- Scope: Unchanged - the substituted command runs inside the access point, within the authority of the
  component whose interface was abused; no crossing into a beyond-device security authority is claimed
- Impact C/I/A: all High - device-root command execution yields the full configuration store, the management
  account set, the wireless and bridge state, and control of service availability
- CWE: CWE-78 primary (OS command injection through a shell-interpreted argument); CWE-798 adjacent and
  disclosed separately (factory-default administrator credentials), which does not raise any metric here
- Published arithmetic: ISS = 1 - (1-0.56)^3 = 0.914816; Impact = 6.42 x 0.914816 = 5.873119;
  Exploitability = 8.22 x 0.85 x 0.77 x 0.27 x 0.85 = 1.234708; sum 7.107827, rounded up to 7.2

Headline: `CVSS:3.1/AV:N/AC:L/PR:H/UI:N/S:U/C:H/I:H/A:H` = 7.2 High.

Privileges Required is High rather than the neighbouring Low tier because the credential this chain consumes
is the device administrator's own, and the record establishes no secondary account class on this firmware
whose web access reaches the `.xgi` route: the `.xgi` predicate and the Basic credential are the same gate for
every principal that can produce the request. A Low rating would describe a principal that the evidence does
not show to exist, and would inflate the score by a tier the chain does not earn. The severity of the
consequence is unaffected by that choice - the substituted command still runs in root context - and the
compensating statement is the one below the score: one authenticated request, no interaction, total device
control, silent.

Rejected reading - Low privileges: `CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H` = 8.8 High.
Arithmetic for that reading: ISS = 1 - (1-0.56)^3 = 0.914816; Impact = 6.42 x 0.914816 = 5.873119;
Exploitability = 8.22 x 0.85 x 0.77 x 0.62 x 0.85 = 2.835255; sum 8.708374, rounded up to 8.8. Rejected
because 8.8 is the arithmetic of a lower-privilege principal, and the published chain requires the device
administrator: no account tier with web access short of administrator is documented in the analyzed
artifacts, so the Low weight has no principal to attach to. The figure is recorded here only so that it is
never quoted as the headline.

## Affected Products

- D-Link DAP-2310B, firmware v3.00r048 (the image analyzed end to end at binary level in this research),
  MIPS 32-bit big-endian, uClibc, stripped; affected component: the `ExeShell` builtin of `sbin/atp`
  (51296 bytes, MD5 `32595db17de80bcedd798cca5b365ec6`) reached through the `.xgi` extension route
- D-Link DAP-2660, firmware v2.00r140 (AC1200 access point): byte-identical merge. `sbin/atp`,
  `/etc/templates/httpd/httpd.php` and `/etc/templates/httpd/httpd_server.php` are byte-identical to the
  DAP-2310B files (MD5 and SHA256 both match on `atp`), so the sink, the validator, the parser, the route and
  the authentication boundary are the same code at the same offsets - one defect, one fix, both models
- Not claimed: other D-Link models sharing the `atp` framework (the DAP-2330 and DAP-2360 families named in
  the research record) were not audited, no hardware revision other than the analyzed image is claimed, and
  no inference is made from model-name similarity
- Verification method and its boundary: firmware-level disassembly and reconstruction established the
  handler, the validator, the decoder, the key match and the parameter gates; dynamic evidence comes from a
  sink-level replication - a native-compiled C program on an isolated x86-64 Linux sandbox reproducing the
  recorded `snprintf(buf, sizeof(buf), "%s > /dev/console", s); system(buf);` construction. Full-device
  emulation was attempted and blocked: `qemu-mips-static` core-dumped with SIGBUS on both the `atp` binary and
  the device busybox `ash`. No physical access point was driven during verification and no live HTTP request
  was sent to hardware
- Privilege ceiling: command execution in the root context the record attributes to `atp`, observed inside
  the replication as `uid=0(root) gid=0(root) groups=0(root)`. Not reached and not claimed: escape from the
  access point to attached hosts, persistence across a factory reset or reflash, radio or driver specifics,
  and any memory-corruption primitive

## Impact

- Complete compromise of the access point at device-root authority by a credential holder who was never meant
  to hold a shell: the management interface becomes an arbitrary-command channel, and everything the device
  can do the attacker can do - wireless configuration, bridge and VLAN state, management accounts, the
  firmware update path, and the `rgdb` configuration store
- Exposure of every secret the device holds for its own operation within readable filesystem scope at root
  authority, including the credential material the httpd template consumes from `/sys/user` and whatever the
  configuration store keeps alongside it
- An interior network position: an access point with root command execution can be turned against the segment
  it serves, consistent with the platform's own capabilities; the extent of that pivot was not tested and is
  not claimed beyond the device itself
- Persistence consistent with root command execution on an embedded Linux system, up to the limits of the
  writable filesystem; what survives a factory reset or a reflash was not tested and is not claimed
- Availability impact at will, from rebooting the radio to removing configuration the device needs to serve
  its segment
- Silent in product terms: one authenticated GET inside ordinary management traffic, with the command's
  output discarded to `/dev/console` rather than returned in the response, so the injection is blind and the
  surviving evidence is the side effect the operator chooses
- Two models, one defect: remediation scoped to the DAP-2310B alone would leave the byte-identical DAP-2660
  exposed, since the vulnerable binary and both httpd templates are the same files

## Mitigation / Fix Recommendations

1. Remove the shell from the path entirely. `ExeShell` exists to run one fixed command, so replace the
   `sprintf` plus `system` construction with an `execve`-family call over a constant argument vector, or
   delete the builtin if no shipped template uses it. This eliminates the class on this surface instead of
   chasing metacharacter sets
2. If a shell has to stay in the path short-term, pass the argument as a single-quoted literal with correct
   single-quote escaping, and reject any value containing `$`, `(`, `)`, backtick or a newline before the
   command is built - the exact characters the current validator at `0x405690` does not inspect
3. Replace the separator blocklist with an allowlist for whatever the parameter is legitimately for. A
   `submit` prefix plus a three-character reject set is not a validation strategy; the accepted grammar
   should be a fixed token, not a prefix of an arbitrary string
4. Drop the `atp` process privileges. The record attributes root context to `atp` because the httpd path
   performs no setuid privilege drop; a dedicated unprivileged identity would not fix the injection, but it
   would cap the blast radius of this and any future defect in the same binary
5. Audit every remaining shell-mediated sink in `atp` for the same pattern, including the second sink the
   record names at `0x405998` (`ConfigGetOnly`, which builds `rgdb -s %s '%s'` with single quotes) and the
   further call sites at `fcn.004041dc`, `fcn.004076f0` and `fcn.0040799c`
6. Add a handler-level regression test: submit a request whose `exeshell` value is `submit$(true)` and assert
   that either the value is rejected or no shell-out occurs; repeat with the newline form `submit%0a` and the
   backtick form `submit%60...%60`, and run the same suite against every model shipping the same `atp` binary
7. Until a patch exists: keep the management plane off any wide-area-facing interface, restrict it to the
   administration segment, and treat the administrator password as the boundary it now is - noting that a
   password change alone does not remove this defect, only the separate default-credential exposure
