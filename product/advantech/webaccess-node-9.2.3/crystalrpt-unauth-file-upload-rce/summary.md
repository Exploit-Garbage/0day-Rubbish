# Advantech WebAccess Node — Unauthenticated File Upload in CrystalRpt.aspx Leading to Code Execution in the IIS Worker Process

Advisory: https://0day-rubbish.com/blog/advantech-webaccess-crystalrpt-unauth-file-upload-rce
Repository: https://github.com/Exploit-Garbage/0day-Rubbish
Contact: disclosure@0day-rubbish.com

## Summary

Advantech WebAccess Node 9.2.3, a closed-source industrial SCADA/HMI web server from Advantech (Taiwan), contains an unrestricted file-upload defect (CWE-434) in the `WaCrpt` Crystal Reports application, compounded by a path traversal (CWE-22) in the destination directory and by the absence of any authorization decision on the hosting page (CWE-306). `CrystalRpt.aspx` performs no authorization decision anywhere in the application: its `Page_Load` validates only that the form fields `projName` and `nodeName` are non-empty, and its failure branch is a `Response.Redirect` to the operator login page rather than an access denial. One evidential gap belongs in the summary, because everything downstream depends on it: the research record holds **no `applicationHost.config` excerpt**, so whether IIS anonymous authentication is enabled for the `WaCrpt` application path on a default install is *inferred and lab-reproduced*, not proven from an artifact. The inference is structural and strong — the product's own login page cannot work unless the hosting site accepts anonymous requests, and the exposure was reproduced against a deployed copy of the shipped application — and PR:N is published on that basis. An administrator who has disabled anonymous authentication on that application path, or fronted it with an authenticating gateway, is not exposed on this vector; the conditional score below prices that configuration. Its button handler `fileSubmit_Click`, in the shipped `bin\WaCrpt.dll`, computes the write destination by concatenating those two form fields into `Server.MapPath("~/report/" + projName + "_" + nodeName + "/")`, gates on nothing but `Directory.Exists(rptDirPath)`, and calls `FileUpload1.SaveAs(filePath)` with no extension validation — before it attempts to open the file as a Crystal Report.

Sending `nodeName = \..\..\` makes `Server.MapPath` normalise the destination to the `WaCrpt` **application root** itself, a directory that always exists, so the `Directory.Exists` gate is satisfied with no report project provisioned and no `report\` directory present. ASP.NET already strips any client-side directory from the multipart `filename`, so the traversal is carried in the *directory* field instead — which nothing filters, because ASP.NET request validation inspects for HTML-dangerous sequences and not for `\` or `..`. Exactly two `..` levels work; three or more are refused with `HttpException: Cannot use a leading .. to exit above the top directory`.

The chain is three requests. Request 1 obtains the page's `__VIEWSTATE` (1056 bytes) and `__EVENTVALIDATION` (92 bytes) while establishing the traversed destination. Request 2 posts a 510-byte ASP.NET page as `FileUpload1` with `fileSubmit=Upload`; `SaveAs` writes it into the application root and `ReportDocument.Load` then throws, so the server returns **HTTP 500 — a red herring, since the write has already completed**. Request 3 fetches the written `.aspx`, which the ASP.NET build manager compiles on first request and executes inside `w3wp.exe`, running `cmd.exe /c <command>` with captured stdout. In the verification environment the execution identity was `nt authority\system`. Two independent client implementations — the research-phase client and a separately written minimal client from a second analysis pass — with two independently written payloads (510 and 450 bytes) reproduced the same result.

Verification was performed by deploying the **shipped `WaCrpt` application** — `CrystalRpt.aspx` (2381 bytes), `Web.config` and `bin\WaCrpt.dll`, the shipped files as documented in the research record, used without modification — into a real IIS site and driving it over HTTP. The record documents the installer and its size and an unpacked deployment archive holding those files, and asserts that they are the real product's; it does not log the extraction step, so no end-to-end provenance chain is claimed. A complete default installation of WebAccess Node 9.2.3 was **not** exercised: the 1.9 GB self-extracting installer hung in Session 0. Consequences carried explicitly through the advisory: the shipped site configuration was authored in the lab rather than read from the installer, the `/broadweb/WaCrpt/...` URL prefix is derived from a literal inside the decompiled `Page_Load` rather than from a request against a stock install, and `nt authority\system` is the identity of the *verification* application pool — the shipped default pool identity is set at install time by `AppPoolAssign.exe` and was not established from any artifact. The transcripts in the analysis are the research-phase client's stdout, preserved by the research record. `exploit/advantech_webaccess_crystalrpt_unauth_file_upload_rce.py` is a parameterised re-implementation of that same chain and is not the tool that produced them.

## CVSS Score

- **Score (primary, published)**: 9.8 Critical, unauthenticated — PR:N rests on the artifact-proven absence of any application-level authorization plus the structural argument and lab reproduction that the hosting site accepts anonymous requests; no extracted installer artifact proves anonymous authentication for the `WaCrpt` application path specifically (see Summary)
- **Vector**: `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H` — recomputed from first principles with the CVSS 3.1 Roundup rule; the figure recorded in the research record for this finding is the figure its own vector computes
- **Conditional reading**: 8.8 High, `CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H` — applies to a deployment where IIS authentication is enforced on the `WaCrpt` application path, in which case the same unvalidated sink and the same traversal are reachable only by an authenticated principal
- **Rejected reading**: 8.1 High, `CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H` — considered because the traversal depth and the mandatory `User-Agent` header are non-obvious, and rejected because both are fixed constants under the attacker's control, which is not the CVSS 3.1 meaning of AC:H

Scope is Unchanged deliberately. The compromise executes as the application-pool identity of the vulnerable product's own web application; the privilege gain crosses a privilege level, not a component's security scope. S:C on these impact values would compute to 10.0 and is not claimed.

## Affected Products

- **Vendor**: Advantech (Taiwan)
- **Product**: Advantech WebAccess — industrial SCADA/HMI web server, critical-infrastructure manufacturing segment
- **Version analysed**: WebAccess Node 9.2.3, from the distributed installer `AdvantechWebAccessNode_9.2.3.exe` (1.9 GB, PE32 InstallShield ScriptDriven self-extracting)
- **Component**: the `WaCrpt` ASP.NET Web Forms application served under `/broadweb/WaCrpt/` — specifically `CrystalRpt.aspx` and `fileSubmit_Click` in `bin\WaCrpt.dll`
- **Scope of the affected-version statement**: 9.2.3 is the only version whose binaries the research record documents as decompiled and exercised; the decompiled sink was confirmed present in 9.2.3, which is *after* the release that fixed a previously published, authenticated upload issue on this product (see Independence). Other versions were not enumerated and no cross-version byte comparison was performed

## Impact

- **Remote code execution requiring no credential and crossing no authorization decision**: three HTTP requests, no user interaction, no race window, no prior server state, and no requirement that any report project be configured. The "no credential" half depends on IIS delivering an anonymous request to the `WaCrpt` application — structurally required by the product's own login page and reproduced in the lab, but not proven from an extracted `applicationHost.config` artifact (see Summary and the conditional score above)
- **Confidentiality High**: full read of the product's configuration, SCADA project tree, served content and database connection material; under the verified SYSTEM identity, additionally the entire filesystem and the local secret store
- **Integrity High**: a generic write primitive placing an attacker-named file with attacker-chosen content into a served, script-executing application directory, plus arbitrary command execution — product binaries, configuration, tag and alarm data and host state are all modifiable
- **Availability High**: the web tier, the SCADA runtime it fronts and the host can be stopped or corrupted, removing operator visibility of the monitored process even where the controlled process keeps running
- **Execution identity caveat**: verified as `nt authority\system` (`S-1-16-16384` System Mandatory Level, `S-1-5-32-544` BUILTIN\Administrators, `SeTcbPrivilege`/`SeDebugPrivilege`/`SeImpersonatePrivilege`/`SeBackupPrivilege` enabled) in the verification pool. The shipped default pool identity was not artifact-established and is not asserted; the RCE holds under either identity, and the identity determines only how much local privilege distance remains afterward

### Independence from previously published advisories

CVE-2025-14849 covers an unrestricted file upload (CWE-434) on this product, scored 8.8 with `AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H` — **PR:L, an authenticated caller** — affecting 9.2.1 with a fix in 9.2.2, and its advisory does not name the affected endpoint. This finding is **PR:N, unauthenticated**, and the unvalidated sink was confirmed by decompilation in **9.2.3**, after that fix. Two readings are consistent with the evidence: the public fix addressed a different upload path and `CrystalRpt.aspx` was never covered (an independent unauthenticated variant), or the fix did not close the unauthenticated route into the same code (an incomplete-fix variant). Without a 9.2.2-to-9.2.3 binary diff, endpoint overlap cannot be excluded to certainty, and this advisory says so rather than claiming more novelty than the evidence carries; the PR:N-versus-PR:L difference and the sibling-file omission evidence (below) carry the independence argument. A separate previously published and vendor-fixed issue, CVE-2018-6911, concerned the `aspvbobj.include` COM helper's `VBWinExec` entry point — a different component and mechanism that this chain never touches, mentioned only to close out the attack-surface enumeration.

The omission evidence: `addTemplate.cs`, a second report-upload handler in the same module, enforces `string.Compare(strA, "RPT", ignoreCase: true) == 0`. `CrystalRpt.cs` does not. Eight sibling files in the module call a session-existence check; `CrystalRpt.cs` does not. Two upload points written for the same feature, one checking and one not, is the signature of an oversight rather than a design decision.

This work is original. The sink, the two-level traversal bound, the mandatory `User-Agent` precondition, the HTTP-500 red herring, the attack-surface enumeration across the product's five web tiers, and the dynamic confirmation were each established independently from the distributed binaries and a deployed instance of them. No prior public writeup was used as a basis.

## Mitigation

1. **Validate the extension in `fileSubmit_Click`** before `SaveAs`, reusing the check `addTemplate.cs` already has — `Path.GetExtension(FileUpload1.FileName)` against a case-insensitive `.RPT` allowlist — and factor it into one shared helper called by both upload points so they cannot drift apart again. A denylist is not an acceptable substitute.
2. **Validate before writing.** `SaveAs` currently precedes `ReportDocument.Load`, so a rejected file is already on disk. Stage uploads to a temporary location outside every application root, parse, and move into place under a server-generated name only on success.
3. **Put a real authorization decision in `Page_Load`** — the `[WaAuth]` filter used by `waconfig90` controllers, or the `isSessionExist` check used by eight sibling files in this module. `Response.Redirect` is not an access decision, the gate must terminate the request, and it must cover the postback path where `fileSubmit_Click` runs, not only the initial render.
4. **Add `<authorization><deny users="?" /></authorization>` to `WaCrpt`'s `Web.config`**, which closes the anonymous route to the whole application without affecting the classic-ASP login page in a different application.
5. **Confine the derived directory.** Reject any `projName`/`nodeName` containing `\`, `/` or `..`, and additionally require `Path.GetFullPath(rptDirPath).StartsWith(canonical report root)` — containment against the `report` subtree specifically, since `Server.MapPath` bounding the result at the application root is not confinement, and the application root is the most dangerous directory in the application.
6. **Stop writing uploads into a script-executing directory**: move report storage outside every IIS application root, or clear handler mappings and deny script execution in the storage subtree, and generate stored names server-side.
7. **Run the application pool under a dedicated least-privilege account**, and remove the pool identity's write access to the application root and `bin\`. Verify the identity the installer assigned rather than assuming it: the shipped installer sets the pool's `IdentityType` at install time through `AppPoolAssign.exe` and the concrete value could not be determined from static strings, so this advisory asserts no shipped pool identity. Isolate whatever genuinely needs elevated host access (industrial hardware, helper processes such as `drawcom.exe`) behind a separate privileged service so the web tier does not need elevated host authority.
8. **Operator mitigations before a patch exists**: disable anonymous authentication for the `WaCrpt` application in IIS while leaving it enabled for the login page; block `/broadweb/WaCrpt/*` at the perimeter or confine the web port to the management VLAN; place file-integrity monitoring on the application root and alert on any new `*.aspx`, `*.asmx`, `*.ashx` or `*.config`; alert on HTTP 500 responses to `CrystalRpt.aspx` POSTs and on `nodeName` values containing `..`; audit the application root for pages not accounted for by the distribution.

## PoC

`exploit/advantech_webaccess_crystalrpt_unauth_file_upload_rce.py` — pure Python standard library, no hardcoded target. `--target` is mandatory; `--port`, `--scheme`, `--path`, `--upload-flag`, `--proj-name`, `--node-name`, `--shell-name`, `--shell-file`, `--payload`, `--marker`, `--user-agent`, `--timeout` and `--form-only` are parameterised. It fetches the form, harvests the ViewState pair, uploads the page, then requests it twice to confirm the execution identity and the marker. Status 500 on the upload is treated as the expected outcome, not as failure.
