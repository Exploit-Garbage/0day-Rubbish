# Circutor LineEds 24.11.14 — Unauthenticated shellExecute Command Injection in the pwrstudio Event Engine (Root Command Execution)

Advisory: https://0day-rubbish.com/blog/circutor-lineeds-pwrstudio-shellexecute-unauth-command-injection
Repository: https://github.com/Exploit-Garbage/0day-Rubbish
Contact: disclosure@0day-rubbish.com

## Summary

The `pwrstudio` daemon shipped in Circutor LineEds (Line Energy Data System) industrial energy gateway firmware 24.11.14-r0 contains an operating-system command injection that lets an unauthenticated remote attacker execute arbitrary commands on the appliance. The daemon's event engine loads its event configuration from `events.xml`, exposed at `/services/user/events.xml` over the management HTTP interface. An event may carry a `shellExecute` action whose `<command>` and `<parameter>` elements are concatenated by `XCEventActionShellExecute::Execute` (`FUN_00548414`) with the wide-string format `"%ls %ls"` at `0x7cc2d0`, converted from wide to narrow, and passed to `system()` at call site `0x5484bc`. Nothing between the socket and the sink neutralises shell metacharacters: no quoting, no filtering, no allowlist. A parameter that begins with `;` therefore closes the first statement and runs an attacker-chosen command, with the trailing `;#` absorbing the remainder as a comment.

Exploitation is two HTTP requests, with no delivery precondition of any kind. The attacker writes one event definition into `/services/user/events.xml`, then requests the `restart.xml` route, which makes the engine reload the document through `XCEventDriver::LoadXml` (`FUN_0020acac`), build the action object, evaluate the always-true `<condition>1==1</condition>`, and dispatch `Execute`. Because the configuration is a file the product persists, the two steps can be separated in time arbitrarily, and the injected event should re-fire on every later engine start — a persistence mechanism built into the product. That persistence is an inference and is published as one: no engine restart was performed during this research, the condition evaluator `FUN_004ce47c` was never run, and the loader chain from the restart route to `XCEventDriver::LoadXml` rests on cross-reference alone. Section 9 of the analysis lists every link established statically rather than executed.

The unauthenticated classification rests on handler-level binary evidence rather than on a configuration assumption. Neither route reaches the product's permission gate `FUN_001a93cc`: a cross-reference census records 197 call sites, all individual action handlers, all inside `0x1aexxx`–`0x1bfxxx`, and both the restart handler (`FUN_001e3554` at `0x1e3554`) and the events write handler (`FUN_0023ace0` at `0x23ace0`) fall outside that set. The restart handler's only guard is `FUN_001a955c`, a three-instruction predicate that returns true when the request object at `+0x34` and the response object at `+0x4c` are both non-null — fields that the dispatcher's own setup routine `FUN_001add40`, installed at offset `+0x0c` of the route entry at `0x76a480`, populates for every request before the handler at `+0x10` is called. It tests object presence, not credentials.

Confirmation used the shipped binary extracted from `pwrstudio_24.11.14-r0-pss0_cortexa7hf-neon.ipk`, run under `qemu-arm-static` user-mode emulation with gdb, because the daemon cannot start its HTTP stack in emulation: its serial initialisation thread loops on `openat("/dev/ttymxc2") = -EACCES`, so the engine-ready futex is never signalled and no thread ever accepts on port 1500. The real sink function was invoked directly with the field values the documented XML schema produces, using a `bx lr` gadget at `0x37510` to neutralise the sub-object virtual copy. It returned 1 and wrote a 39-byte root-owned marker containing `uid=0(root) gid=0(root) groups=0(root)`. A control run with a benign 25-character parameter reached the same sink, returned the same value, and wrote nothing. **End-to-end HTTP exploitation was not performed, no request was ever delivered to `pwrstudio`, and no physical device was used**; the HTTP delivery path is proven statically, from the route table, the handler decompilations and the caller census.

This advisory concerns the Linux ARM `pwrstudio` binary only. It is not a claim about the vendor's separately-built Windows PowerStudio SCADA WAVE platform, which is a different binary, on a different operating system, reaching process creation through Win32 APIs, and which is the subject of separate published research of our own. The shared `"%ls %ls"` format and shared `shellExecute` action name reflect one engine design carried across two platforms, not shared code.

## CVSS Score

- **Score**: 9.8 Critical — primary, unauthenticated reading
- **Vector**: `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`
- **Conditional score**: 8.8 High — `CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H`, applying where a deployment rejects anonymous configuration writes (security enforcement enabled, or the events handler's 401 branch active); nothing else in the chain changes
- **Class**: CWE-78 (OS command injection) plus CWE-306 (missing authentication for a critical function) — the two recorded in the research for this finding — with CWE-285 (the permission gate fails open both at `perm != 0x15` and at toggle-off) and CWE-20 (no schema validation on write) added as contributing weaknesses by this advisory's own classification
- **Scope**: Unchanged — the command runs inside the same device authority the daemon already holds; a reader who counts the appliance OS as a separate realm would score `S:C` at 10.0 Critical, and we do not adopt that reading

Two claims carried by the research record are deliberately not published as fact. First, that the daemon's security enforcement is off *by default*: no shipped artifact supports the default value — no configuration file inside the image, no value read from the extracted root filesystem, not the contents of the `engine.xml` package, and no vendor documentation of the factory setting. The unauthenticated classification does not depend on it, because neither route in the chain invokes the gate at all; the default only matters for the alternative `reloadCfg.xml` trigger, whose reload action does call `FUN_001a93cc(param_1, 0x15, ...)`, and that variant is treated as conditional. Second, that `pwrstudio` runs as `root` on a device: the observed `uid=0(root)` is the privilege of the root-run emulation harness, and the device-side account is inferred from the daemon's ownership of the restart, reload and upgrade routes, since no init script or service unit was extracted. Neither caveat alters the impact metrics.

## Affected Products

- **Vendor**: Circutor S.A. (Spain); **product**: LineEds (Line Energy Data System) industrial energy gateway
- **Firmware verified**: 24.11.14-r0, engine variant `pss0`. Only this build was extracted, disassembled and executed; every offset quoted is specific to it
- **Affected component**: `/usr/bin/pwrstudio` — a 9.1 MB ARM 32-bit LSB ELF EABI5 executable, stripped, non-PIE `EXEC`, entry point `0x37394`, dynamically linked against libpthread, librt, libstdc++, libm, libgcc_s and libc, byte entropy 6.122 (not packed), compiled with `CONFIG_NO_HASP` so no licence dongle gate stands between a written event and the shell action
- **Extracted from**: `pwrstudio_24.11.14-r0-pss0_cortexa7hf-neon.ipk`, inside the vendor `.upgrade` image, which is a POSIX tar also containing the `dropbear`, `engine.xml`, `firmware`, `forwardproxy-service`, `nginx`, `signature` and `wifi-watcher` packages
- **Broader applicability is inference, not verification**: the `pss0` variant marker implies sibling engine variants, and the class inventory (`XCEventActionShellExecute`, `XCEventDriver`, `XCEventServer`, `XCEventSystem`, `XCEventServerGroup`) is a framework rather than a per-model implementation, so other LineEds firmware revisions or other appliances embedding this engine are plausibly affected. No second image was extracted and no second build was disassembled; validate your own build
- **Network exposure**: the daemon's own HTTP listener on port 1500, behind the `nginx` reverse proxy evidenced by the package in the same archive, exposing roughly 28 routes including `/api/v1/login`, `/services/user/events.xml`, `/services/user/eventsInfo.xml`, `/services/events/acknowledge.xml`, `/services/events/listener.xml`, `/services/events/producer.xml`, `restart.xml`, `reloadCfg.xml` and `/upgrade.cgi`

## Impact

- **Arbitrary command execution on an industrial energy gateway**, with the daemon's privileges, reachable with two ordinary HTTP requests and no exploitation reliability concerns — no race, no memory-layout dependency, no need for a file to be pre-placed on the target
- **Confidentiality High**: every measurement record, configuration item, credential, certificate and key on the appliance becomes readable, including whatever it holds to authenticate to the energy-management back office; a compromised gateway is also an ideal passive collection point for the measurement traffic it forwards
- **Integrity High**: measurement data can be altered in transit or at rest before reaching the back office, so forged consumption, generation or power-quality figures propagate into reporting, settlement, alarm thresholds and control decisions while arriving through the legitimate path; event configuration can be rewritten and firmware pushed through the same management plane
- **Availability High**: the attacker controls the very restart and reload primitives the chain uses, and can reboot the appliance on demand, stop measurement collection, drop configuration or wedge the engine, producing a data outage in the metering path
- **Persistence and lateral movement High in practice**: on the inference flagged above and not directly observed, the written event would re-fire on every subsequent engine start, including operator restarts, watchdog events and power cycles, giving a foothold inside the OT segment on a device that security tooling normally treats as trusted instrumentation

## Mitigation

1. Remove the shell from the execution path: replace `system()` in `XCEventActionShellExecute::Execute` with `execve()` or `posix_spawn()` and an explicit argument vector, and delete the `"%ls %ls"` concatenation with it — this removes the class, not the instance
2. If shell execution must be retained, constrain both elements against an allowlist: validate `<command>` as a path to an executable in an allowlisted directory and reject `;`, `|`, `&`, backtick, `$`, `<`, `>`, parentheses, braces, newline, carriage return and backslash in `<parameter>`, enforcing the check at construction (`FUN_00548414`) and not only at load
3. Make the permission gate fail closed: `if (perm != 0x15) return SUCCESS;` should deny and log any permission value the gate does not recognise, instead of granting by default on unknown input
4. Take administrative routes out of the security toggle's reach: event-configuration write, device restart, configuration reload and firmware upgrade should require authentication unconditionally, so no compatibility switch can disable authorization for them
5. Move authorization into the dispatcher with an explicit per-route permission table, so a new handler cannot be unauthenticated by omission — the current design has 197 handlers calling the gate individually, and the two handlers in this chain are the ones that did not
6. Validate the events document against a schema at write time in `FUN_0023ace0`, rejecting unknown element names, unknown action types and out-of-set characters; this also turns the handler's currently unexplained 401 branch into a documented rejection path, and reconsider whether a raw shell action belongs in a gateway build at all
7. Run the daemon with least privilege, splitting the network-facing handler from the privileged action executor, so a command injection becomes a bounded failure instead of full appliance compromise
8. Operator measures until a fixed build exists: restrict the management plane to a dedicated out-of-band network and firewall port 1500 plus the reverse proxy to a short allowlist; place it behind an authenticating proxy or VPN; inspect `events.xml` on every appliance and alert on any `shellExecute` action whose command is not a known maintenance script or whose parameter contains `;`, `|`, backtick, `$(`, `>` or newline; and monitor for a write to `/services/user/events.xml` followed within seconds by a request to `restart.xml` or `reloadCfg.xml` from the same source, which is this chain's signature
