# CloudPanel 2.5.4-3 - nginx Virtual-Host Configuration Injection in the Site-Settings Root Directory Field (CWE-93)

Advisory: https://0day-rubbish.com/blog/cloudpanel-site-rootdirectory-nginx-vhost-injection-root-rce
Repository: https://github.com/Exploit-Garbage/0day-Rubbish
Contact: disclosure@0day-rubbish.com

## Summary

CloudPanel Community Edition, from cloudpanel.io (Germany), is a closed-source server-management panel for VPS and dedicated hosting that provisions and supervises nginx, php-fpm, MariaDB and hosted web sites from a Symfony web application on port 8443. The site-settings form field `site_domain_settings[rootDirectory]` carries no character-level validation at all, so a value holding real newlines is written verbatim into the database, rendered verbatim by the virtual-host processor `src/Site/Nginx/Vhost/Processor/RootDirectory.php` at goto label `b9892`, and written verbatim into `/etc/nginx/sites-enabled/<domain>.conf` by `src/System/Command/Vhost/WriteFileCommand.php` at label `Dc4ef` (`echo %s | /usr/bin/sudo /usr/bin/tee %s`, both substitutions passed through `escapeshellarg`). The product then reloads nginx on its own initiative, and the vendor-built `nginx-common 1.30.4-1+clp-bookworm` package reads `/etc/nginx/nginx.conf`, whose line 119 is `include /etc/nginx/sites-enabled/*.conf;` and whose line 1 is literally `user root;`. An injected `location` block with `dav_methods PUT; create_full_put_path on;` therefore yields an anonymous WebDAV write primitive, and a second injected block with `fastcgi_pass unix:/run/clp-fm-php-fpm.sock;` forwards PHP execution to the File Manager php-fpm pool that the same package ships with `user = root` in `/home/clp/services/php-fpm/fpm/pool.d/file-manager.conf`. A low-privileged panel user holding only `ROLE_USER` and owning one site achieves arbitrary OS command execution as host `uid=0`, with the write primitive and the execution request both issuing anonymously and no administrator involvement after the initial authenticated save.

- **Component**: the nginx virtual-host renderer reachable from `POST /site/{domainName}/settings` (Symfony route `clp_site_settings`), plus the packaged site-facing nginx and File Manager php-fpm pool that amplify the injected text.
- **Sink and source**: sink is the `{{root}}` placeholder substitution in `RootDirectory.php` label `b9892`, `rtrim(sprintf("root /home/%s/htdocs/%s;", $siteUser, $rootDirectory), "/")`, whose `rtrim` is dead code because the format string always ends with `;`; source is the `rootDirectory` text field of the `site_domain_settings` form, whose only declared constraint is `Assert\NotNull` and whose entity setter at `src/Entity/Site.php:404-406` performs no sanitization.
- **Sanitization**: none on this field. The same form family validates `$domainName` with a dedicated `AppAssert\DomainName` constraint whose pattern excludes `/` and `\`; the command-line channel clamps the identical value with `ltrim(rtrim($x,"/"),"/")`; and a neighbouring free-text field, `additionalConfiguration`, has a four-step `PRE_SUBMIT` normalization that rewrites `"` to `'`. The web-channel `rootDirectory` value passes through none of these.
- **Classification**: CWE-93 injection of control characters into a configuration file that is later parsed as nginx directives. This is not command injection: both `%s` substitutions in the writer command are `escapeshellarg`'d, so no shell metacharacter reaches a command line. The defect is entirely in the configuration-text layer, and the code execution comes from the semantics of the injected nginx directives.

## CVSS Score

- **Score**: 8.8 High (CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H) - a remote authenticated panel tenant reaches arbitrary OS command execution as host root with no user interaction, and every element of the chain is installed by the vendor's own packages.
- **AV:N** - the whole chain is HTTP: one authenticated `POST`, one anonymous `PUT`, one anonymous `GET`. No local shell and no adjacent network position is required.
- **AC:L** - there is no race, no memory-corruption reliability question and no timing window. The only payload constraints are syntactic validity and the presence of `include /etc/nginx/fastcgi_params;`, both of which the reference exploit produces deterministically; the injection landed on the first attempt in five independent rounds and every configuration it depends on is vendor-installed, not operator-enabled.
- **PR:L** - the least privileged principal proven to reach the sink holds `ROLE_USER` only, the lowest panel role, and four distinct `ROLE_USER` identities performed five injection rounds across two reproduction sets. `config/packages/security.yaml` has no `role_hierarchy`, the settings page is not under `^/admin`, and `src/Controller/Frontend/SitesController.php` declares `ROLE_USER` exactly once. This is `PR:L` and not `PR:N` because no authentication bypass reaching this sink exists, and not `PR:H` because `ROLE_ADMIN` was never needed for the injected request.
- **UI:N** - nothing in the chain needs another user's action.
- **S:U** - see the Scope note below.
- **C:H / I:H / A:H** - host `uid=0` execution yields unrestricted read of every file on the host, unrestricted modification of host and product state, and unrestricted ability to stop any service.
- **Scope**: Unchanged. A Changed-scope reading is genuinely tempting here, because the vulnerable component is the panel application authorised to a tenant role while the achieved impact lands on the host operating system and on every other tenant sharing it. We publish Unchanged for two reasons. First, the privilege ceiling is produced entirely by the vendor's own configuration choices - `user root;` in the vendor nginx configuration, `user = root` in the vendor File Manager pool, and `clp ALL=(ALL) NOPASSWD: ALL` in `/etc/sudoers.d/cloudpanel` - so the escalation never leaves an authority the product itself established. Second, the cross-tenant consequence is a capability inference: we did not run the verification on a host with a second tenant installed and we did not measure impact on another tenant. Publishing a Scope-Changed headline on an untested cross-tenant claim would overstate the evidence. The Changed-scope vector is recorded in section 12 of the analysis as a rejected reading, with no score attached.
- **CWE**: CWE-93 (primary; improper neutralization of CRLF sequences, here control characters injected into a configuration file). Contributing: CWE-20 (absent input validation on the field), CWE-269 and CWE-250 (the File Manager php-fpm pool and the site-facing nginx worker user both run as root, which is what converts a configuration write into host-root execution). Reported separately and never folded into this vector: CWE-338 (the panel "Generate Password" button uses `Math.random()`).
- **Recorded-score note**: no correction is needed. The computed value of the published vector under the CVSS 3.1 formula is the value printed above. Derivation from first principles: ISS is 0.914816, Unchanged impact is 5.873119, exploitability is 2.835255, the sum is 8.708374, and rounding up to the nearest tenth yields 8.8.
- **Conditional reading**: none is published. There is no deployment state we identified that makes this chain unauthenticated, and we do not publish a hypothetical higher score for one.

## Affected Products

- CloudPanel Community Edition **2.5.4-3+clp-bookworm**, from cloudpanel.io (Germany). The distribution package examined is 69,183,476 bytes with md5 `24c36a4739ce065c5c188c89def06f29`.
- Closed source, established from the artifact rather than inferred: `composer.json:3` reads literally `"license": "proprietary"` (file md5 `568641dea8f40aacb6a4b24a067b825a`). The package ships `/usr/share/doc/cloudpanel/` with only `changelog.Debian.gz` and no copyright file, and the application source carries no copyright headers.
- Affected component: the site-settings form and the nginx virtual-host renderer that consumes it - `src/Form/SiteDomainSettingsType.php`, `src/Entity/Site.php:404-406`, `src/Site/Updater.php` label `f807c`, `src/Site/Nginx/Vhost/Processor/RootDirectory.php` labels `Aca8b`, `b9892` and `e35ff`, and `src/System/Command/Vhost/WriteFileCommand.php` label `Dc4ef`. Amplifier components: the vendor `nginx-common 1.30.4-1+clp-bookworm` package (`/etc/nginx/nginx.conf` line 1 `user root;`, line 119 `include /etc/nginx/sites-enabled/*.conf;`, md5 `6727bffeb96cb3e03b85d00eac39c47c`, 3,077 bytes) and `/home/clp/services/php-fpm/fpm/pool.d/file-manager.conf` (md5 `83e79f2f3de4afad76c0b0a4666dcb89`).
- Runtime stack: Debian bookworm x86_64; PHP 8.1 for the panel pool and the File Manager pool; Symfony 6.0; MariaDB for hosted databases with the panel's own state in SQLite at `DATABASE_URL="sqlite:////home/clp/htdocs/app/data/db.sq3"`; site-facing nginx 1.30.4 from the vendor package and a separate panel nginx on port 8443.
- Only this build was tested. No other version, edition or deployment target is claimed, in either direction.
- Verification method and boundary: static analysis of the installed package plus dynamic reproduction inside a single-container testbed built from the vendor `.deb`, with the vendor nginx, MariaDB and sudo present and with published ports bound to loopback only. Five end-to-end rounds were observed. Because the container has no init system as PID 1, first startup of MariaDB, both nginx instances and php-fpm was a test-harness action, and the one file we replaced on disk was `/bin/systemctl` - a 1,353,368-byte binary owned by the `systemd` package, md5 `40621176f9df719abc43a35a08983631`, replaced by a 35-line shim that reads `ExecReload` from the vendor unit at run time. `dpkg -V cloudpanel` afterwards reported only a runtime log difference and `dpkg -V nginx-common` was empty, so no product file was modified. The chain hops themselves - form save, the product's own reload, anonymous `PUT`, anonymous `GET` - were all performed by product code over vendor-native wiring, with all 11 recorded reload invocations carrying `SUDO_USER=clp` and none originating from the harness.
- Privilege ceiling: host `uid=0` was reached and is evidenced by a live `id`, by `posix_getuid()` and `posix_geteuid()` returning 0, by `whoami` returning `root`, and by the uploaded file landing as `-rw------- 1 root root`. The executed identity string is `uid=0(root) gid=1000(clp) groups=1000(clp),0(root)`, which is exactly the shape the packaged pool directive pair `user = root; group = clp;` produces. Not reached, and not claimed: `ROLE_ADMIN` panel scope (the chain does not need it), a second tenant on the same host, and any deployment where `/run/clp-fm-php-fpm.sock` or the File Manager pool has been reconfigured away from root - on such a host the write primitive remains but execution privilege would be reduced, and that configuration was not tested.

## Impact

- Arbitrary OS command execution as host `uid=0` on the machine running the panel. On a hosting server that is total compromise: every hosted site's document root, every site system account, the panel database, all TLS private keys, all SSH keys, the sudoers drop-in and every systemd unit are inside the achieved boundary.
- Credential and secret exposure. The executed identity reads `/home/clp/htdocs/app/files/.env` (containing the factory static `APP_SECRET`), the panel's SQLite database holding password hashes and API tokens, `var/sessions/sess_*`, and `/etc/sudoers.d/cloudpanel`. In the authoritative round the marker body returned the sudoers contents verbatim, including `clp ALL=(ALL) NOPASSWD: ALL`.
- Cross-tenant blast radius. CloudPanel is a multi-tenant hosting panel and the start identity is the tenant-level role, so one tenant's single form save compromises every other site on the same host. This is stated as a capability inference, not as a measurement: no second tenant was present during verification.
- Persistence and detection avoidance. The two follow-up requests are anonymous and unauthenticated once the injection is in place, the injected directives live inside a legitimate product-managed configuration file owned by root, and the marker file is written under `/tmp` with mode `0600`. There is no product log entry for the injection itself, because the save handler returns `302` with no error on success semantics.
- Availability. `ServiceReloadCommand::isSuccessful()` returns `true` unconditionally and the reload is backgrounded with `&`, so a failed reload is invisible to the product. A syntactically illegal payload is therefore written to disk without rollback and without any `nginx -t` on this code path, leaving a configuration that makes the next nginx restart fail - a persistent denial-of-service condition we report as a separate disclosure item and deliberately do not fold into the code-execution score.
- No administrative involvement is needed after the initial authenticated save, and no factory credential is involved anywhere: the product ships in a zero-user state and the first administrator is created through the install wizard at `/admin/user/creation` behind an `if (!count($users))` gate. The panel account used in verification was seeded by us and is not a factory default, which is what keeps this finding in the post-authentication category rather than the default-credential category.
- Detection caveats. The observable signals are unusual: a `rootDirectory` column value containing newlines, a virtual-host file whose size grew and whose `grep -n` output contains `dav_methods` or a `fastcgi_pass` at a line the templates never emit, `PUT` and `MKCOL` verbs in the site-facing access log for a hosting tenant that has no reason to use WebDAV, and rotated nginx worker pids. None of these are surfaced by the panel's own UI as an error.
- Contributing weakness, reported separately. The panel's "Generate Password" button at `public/assets/js/common.js:18-29` (md5 `6c62f220ae588ea8dee2b922fb4cffbe`, 2,778 bytes, 96 lines) derives credentials from `Math.random()`, which appears twice in that file while `getRandomValues` appears zero times. It is called from 17 templates covering site users, SSH users, FTP users, database users, panel users and Basic-Auth, and the server-side construction `md5(uniqid(rand(), true))` appears at `public/phpmyadmin/login.php:40` and `:42`. Passwords for panel and database accounts generated this way are low-entropy by construction. We label it a weak randomness source with predictability not empirically demonstrated, and we do not raise the score of this advisory because of it.

## Mitigation

1. Add a character-level validator to the `rootDirectory` field, mirroring what the same form family already does for `$domainName` with `AppAssert\DomainName`. An allowlist of `[A-Za-z0-9._-]` is sufficient; at an absolute minimum reject newline, carriage return, `{`, `}`, `;`, the comment character, quotes, whitespace and any leading traversal sequence. Apply the validator on the web channel, because the command-line channel already clamps the same value with `ltrim(rtrim($x,"/"),"/")`.
2. Fix the dead sanitization. `rtrim(sprintf("root /home/%s/htdocs/%s;", $siteUser, $rootDirectory), "/")` can never strip anything, because the format string ends with `;` and therefore its result can never end with `/`. Sanitize `$rootDirectory` before the `sprintf` call, not after it.
3. Treat every virtual-host placeholder as a structured-configuration sink, and validate the rendered artifact rather than only the template. Put one shared line-oriented allowlist normalization in front of all processors, covering `{{root}}`, the `{{settings}}` placeholder written by `addPageSpeed()` and `{{php_settings}}`; extend the existing template-structure check in `src/Command/VhostTemplateAddCommand.php` (`requiredPlaceholders` is currently `["server_name", "root"]`, which validates that the placeholders exist but says nothing about the values substituted into them); run `nginx -t` on the rendered virtual-host file in a temporary location and install it only if the test passes; and route every write through `updateNginxVhostWithRollback()`, which already exists in the product and already contains `NginxConfigTestCommand`, `CopyFileCommand`, a `.conf.bak` artifact and an invalid-configuration exception, instead of the bare `updateNginxVhost()` that `Updater::domainSettings()` currently calls.
4. Make failure observable. `ServiceReloadCommand::isSuccessful()` must not `return true;` unconditionally, and the reload should not be backgrounded with `&` when the caller reports success based on nothing.
5. Separate privilege. Do not run the File Manager php-fpm pool as `user = root`; drop it to the panel account or a dedicated unprivileged user, set `security.limit_extensions` explicitly rather than relying on the php-fpm compiled-in default, and tighten `srw-rw---- root clp /run/clp-fm-php-fpm.sock` so that a site-facing nginx worker cannot address the pool. Lower `/etc/nginx/nginx.conf` line 1 from `user root;` to an unprivileged worker user. Neither change removes the injection, but together they cap the outcome of any future configuration injection at the panel account.
6. Audit the rest of the command-builder family. Of the 49 command builders under `src/System/Command/`, 44 already pass their arguments through `escapeshellarg`, which protects command lines but does nothing at all for configuration text. Every builder whose output is a configuration file rather than a command line needs the value-level allowlist from item 1.
7. Do not import runtime configuration from a remote repository into a database row that is later interpolated with user-supplied values. `postinst.sh:97` runs `clpctl vhost-templates:import`, which performs `git clone` of `APP_VHOST_GIT_REPOSITORY` and stores the template text in the SQLite `vhost_template.template` column. Shipping the templates inside the package would remove both a supply-chain dependency and an integrity question independent of this finding.
8. Ship a regression test that saves a `rootDirectory` containing a newline, a semicolon, a brace pair and a comment character and asserts the save is rejected, plus a test that renders a virtual host from a hostile value and asserts `nginx -t` fails before installation, plus a test asserting that no packaged pool file declares `user = root`.
9. Operator measures until a patch exists: treat every panel account that owns a site as holding host root, because that is what this finding proves; restrict who can hold such an account and put the panel listener behind VPN, single sign-on or a source allowlist; after every site-settings save, diff `/etc/nginx/sites-enabled/*.conf` against a known-good baseline and alert on any newly appearing `location`, `dav_methods`, `alias`, `root` or `fastcgi_pass` directive; alert on `PUT`, `MKCOL` and `PROPFIND` verbs in the site-facing access log; alert on `directive "root" is not terminated by ";"` and on `[emerg]` at nginx startup, which both mean a poisoned configuration is on disk and the next restart will fail; validate configuration independently with `nginx -t` rather than trusting panel-reported success; keep a backup of `/etc/nginx/sites-enabled/`, because the product keeps no `.bak` on this code path; and rotate every credential ever produced by the "Generate Password" button, because it is derived from `Math.random()`.
