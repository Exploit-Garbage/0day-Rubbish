# SmartBear Collaborator Server 15.1.15101 - Path Traversal (Zip-Slip) in the DOORS/Simulink Review-File Upload Leading to Groovy Server Page Execution (CWE-22)

Advisory: https://0day-rubbish.com/blog/smartbear-collaborator-doors-upload-zip-slip-webroot-gsp-rce
Repository: https://github.com/Exploit-Garbage/0day-Rubbish
Contact: disclosure@0day-rubbish.com

## Summary

SmartBear Collaborator Server 15.1.15101 is a closed-source peer and technical code-review platform running as a Java web application on Apache Tomcat. Its JSON-API command `ReviewService.addDoorsFiles` accepts a zip archive from any authenticated user and hands it to the first-party extractor `com.smartbear.ccollab.doors.DoorsFilesUploadService.upload`, whose only validation of an entry is that the entry object is not null (`:73-75`) and whose only filter is the keyword `__MACOSX` (`:63`, `:79`). The entry name is passed through a cosmetic square-bracket substitution at line 77 and concatenated into a destination at line 78 with `new File(uploadContext.getDestVersionDir(), fileName)` - no `normalize()`, no containment test against the destination, no rejection of parent-directory sequences - and written at line 84. An entry named `../../../../../webapps/ROOT/name.gsp` therefore escapes the per-review version directory, whose depth is fixed and predictable, and lands in the Tomcat webroot, where the ROOT webapp's own `web.xml:271-278` maps `*.gsp` to the upstream `groovy.servlet.TemplateServlet` on the anonymous surface. A plain unauthenticated GET of that path compiles and evaluates the page, which converts a post-authentication arbitrary-file-write into unauthenticated-triggerable OS command execution inside the product's own JVM as `uid=1001(collab) gid=1001(collab) groups=1001(collab)` - a non-privileged service account, not root and not a system account. One shipped deployment shape blocks the chain, and operators should read that before assessing their exposure: in the pristine official container image the destination mount point is `drwxr-xr-x 2 root root` while the service runs as uid 1001, so `Files.createDirectories` at `HtmlBaseFilesUploadService.java:77` fails with `EACCES` on the first filesystem call and no byte is ever written.

- **Component**: `ReviewService.addDoorsFiles` over `POST /services/json/v1`, dispatching through `ReviewServiceImpl.addZipFiles:969-1001` to `DoorsFilesUploadService.upload`; the sibling `com.smartbear.ccollab.matlab.SimulinkFilesUploadService.copyFilesFromZip:186-203` shares the same root cause at `:188` and is reachable from `ReviewService.addSimulinkFiles`, but was not exercised end to end and carries two further gates.
- **Sink and source**: the sink is `new FileOutputStream(entryDestination)` at `DoorsFilesUploadService.java:84`; the source is `zipEntry.getName()` at `:77`, carried in a `multipart/form-data` body whose file part name must equal the declared `zipName` verbatim. The execution half is `groovy.servlet.TemplateServlet`, mapped by first-party configuration, reached by anonymous GET.
- **Sanitization**: `Strings.replaceSquareBracketsToRound` at `:77` rewrites brackets to parentheses for the DOORS parser; `IGNORE_FILES_KEYWORDS = {"__MACOSX"}` skips macOS metadata. Neither is a path control. The restricted-file-pattern check that does exist lives only in the sibling servlet `VersionContentUploadServlet:90-93`, and only on the JSON-API-free route.
- **Why this is post-authentication**: an anonymous `ReviewService.addDoorsFiles` call returns HTTP 200 with a 127-byte `AuthenticationError`, and a non-administrator account with `"admin":false` completed the whole chain. A separate anonymous initialisation route that yields factory administrator credentials holds only on a never-initialised instance and was tested twice to be idempotent - replay neither wipes the database nor resets a changed administrator password - so it cannot support an unauthenticated reading.

## CVSS Score

- **Score**: 7.5 High (`CVSS:3.1/AV:N/AC:H/PR:L/UI:N/S:U/C:H/I:H/A:H`) - recomputed from first principles with the CVSS 3.1 round-up rule; Impact 5.87311872 plus Exploitability 1.62014556 equals 7.49326428, which rounds up to 7.5. Attack Complexity is High on the headline because the only shipped artifact actually exercised is the vendor's official container image, and in that image used exactly as shipped the chain is blocked: the webserver directory is a declared volume that the installer never creates, so the container runtime creates the mount point root-owned while the service runs as uid 1001, and `Files.createDirectories` at `HtmlBaseFilesUploadService.java:77` fails with EACCES on the first filesystem call of the whole feature. The shape in which the chain does work is the native, non-container install, and that shape was never verified - the vendor's native installer was never run on a real host - so its writability rests on a structural inference from the shipped archive rather than on an observation. Exploitability cannot be rated Low as the headline when the one deployment shape that was tested does not permit the chain. This is the honest rating, not a pessimistic one.
- **Attack Vector: Network** - all three requests travel over TCP to the product's single HTTP listener on port 8080; no local or adjacent access is needed.
- **Attack Complexity: High** - not because the traversal is subtle: the depth is a deterministic function of values the attacker controls or is returned, there is no race and no state to gather. It is High because success depends on a condition the attacker neither controls nor can verify from the product - that the upload tree is writable by the service uid. On the one shipped artifact exercised, the official container image used as shipped, that condition is false: the runtime-created `VOLUME` mount point is `drwxr-xr-x 2 root root` against a service running as uid 1001, and the feature's first filesystem call fails with EACCES. On the shape where the condition is believed to hold, the native install, it was never observed. The Low argument that does exist - `HtmlBaseFilesUploadService.java:77` creates the destination tree itself, on the line before the first archive entry is read, so writability is implied by the attacked feature being usable at all - is preserved as the justification for the conditional reading below, not for the headline.
- **Privileges Required: Low** - any authenticated principal. A non-administrator account completed the chain twice. Administrator status is neither needed nor helpful, since an administrator is by default refused review creation, so this metric is not a conservative choice.
- **User Interaction: None** - the attacker issues the triggering GET; no victim action is involved.
- **Confidentiality / Integrity / Availability: High** - unsalted ASCII-MD5 password digests for every account, the database superuser credential, all integration secrets decryptable with a constant key embedded at `EncryptUtils.java:31-32`, all review content; arbitrary code execution plus arbitrary file write across the whole installation tree; the service account owns the Tomcat tree, so application and database files can be destroyed.
- **Scope**: Unchanged. Write and evaluation happen in the same JVM, the same web application and the same uid 1001, over directories that account already owns. That an anonymous client can trigger execution is a fact about who pulls the trigger, which Attack Vector and User Interaction already capture; no resource under a different security authority is affected.
- **CWE**: CWE-22 (path traversal via archive entry names) primary; CWE-94 (code generation through the `*.gsp` template mapping), CWE-732 (webroot and content volume both service-owned and traversally adjacent; the inverse defect in the container shape is a root-owned `VOLUME` mount point), CWE-693 (the global `AuthTicketFilter` defaults to allow at `:128` and its single 401 branch does not cover webroot paths), CWE-668 (the only shipped template sits in the webroot rather than under `WEB-INF`) and CWE-916 (unsalted MD5 password digests) contributing. CWE-916 and the other contributing weaknesses are disclosed but deliberately not folded into the vector.
- **Recorded-score correction**: the rejected Scope-Changed reading of this chain was recorded during analysis as 9.9. Under the CVSS 3.1 Scope-Changed impact formula the same metrics give 10.0; 9.9 is the CVSS 3.0 result, whose polynomial term differs. Scope-Changed is rejected on the merits, so neither figure is published as a score.
- **Conditional reading (labelled as such)**: 8.8 High, `CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H`, applicable where the upload tree is writable by the service uid - the native install shape and any container deployment where that volume was created with service-account ownership. There Attack Complexity is Low on a real argument: `HtmlBaseFilesUploadService.java:77` creates the destination tree itself on the line before the first archive entry is read, so in that shape the precondition is implied by the attacked feature being usable at all, and an attacker who can call `addDoorsFiles` and get anything other than a permission-derived `InternalError` is already in the exploitable shape. It is published as the conditional and not as the headline because that shape was never verified on a real host. Both readings are High, and neither says this is remotely exploitable without an account.

## Affected Products

- SmartBear Collaborator Server, verified build 15.1.15101, self-reported in its startup log as `Starting Collaborator Enterprise 15.1.15101.220`, with four shipped artifacts carrying the suffix `*-15.1.15101.jar`, from SmartBear. The artifacts examined in this research do not establish the vendor's country of incorporation or headquarters, so none is stated here.
- Affected component: the DOORS/Simulink review-file upload extractor family - `com.smartbear.ccollab.doors.DoorsFilesUploadService.upload` and `com.smartbear.ccollab.matlab.SimulinkFilesUploadService.copyFilesFromZip` - reached from the JSON-API commands `ReviewService.addDoorsFiles` and `ReviewService.addSimulinkFiles`, with the destination computed by the shared parent `HtmlBaseFilesUploadService.createUploadContext`.
- Runtime stack: Ubuntu 26.04 LTS base, OpenJDK 11.0.31+11 under an install4j launcher, Apache Tomcat with the `http-nio-8080` connector, HSQLDB in-process via `jdbc:hsqldb:file:` with no listening port, no reverse proxy, and upstream Groovy `groovy.servlet.TemplateServlet` mapped to `*.gsp` by the ROOT webapp's own `web.xml:271-278`.
- **Deployment shape that is blocked**: with the vendor's official Docker image used exactly as shipped, the chain does not work. That image declares the webserver directory as a `VOLUME`, and because the installer never creates it, the container runtime creates the mount point as `drwxr-xr-x 2 root root` while the service runs as uid 1001. The first filesystem call, `Files.createDirectories(destVersionDir.toPath())` at `HtmlBaseFilesUploadService.java:77`, fails with `EACCES`; the JSON-API answers HTTP 200 with a 127-byte `InternalError` whose message is only the destination path, a filesystem-wide search for the marker returns zero hits, and the anonymous GET returns 404 with 653 bytes. This is a packaging artefact, not a product defence, and it cannot be worked around through product configuration because `setWebserver` has exactly one call site, at startup, from the `content-webserver` context parameter at `ROOT.xml:92` with `override="false"`.
- **Deployment shapes where the chain succeeds**: those in which the upload tree is writable by the service uid, which is the native, non-container install shape and any container deployment where that volume was created with service-account ownership. The chain was demonstrated there by bind-mounting a host-side directory that held zero entries, performing no ownership, permission or directory-creation command inside the container, and observing the product create `doors/<rid>/<zipbase>/ver1` - four nested directories plus one file, all owned by uid 1001 - and then execute the escaped `.gsp` anonymously.
- Only build 15.1.15101 was tested. No other version, edition or platform is claimed, and no cross-version statement of any kind is made.
- Verification method and its boundary: static reconstruction from a 4457-file decompiled corpus of the shipped archives, plus end-to-end dynamic verification against instances of the vendor's published container image (loaded from a 1795588608-byte archive) published on loopback addresses only. Four mutually independent execution records exist, three of them with fresh random marker tags and fresh review identifiers. The boundary is that **the vendor's native installer was never run on a real host**, so the claim that a native install leaves the webserver directory owned by the service account is a strong structural inference from three observations - the installer archive contains no `chown` at all and its two directory-creating classes change no ownership; the product necessarily creates that tree itself; and a comparable runtime directory in the same image is created by the product as `1001:1001` - and not a measurement. All request traffic originated from loopback and no re-test from a non-loopback source address was performed. A fully initialised and licensed instance was never used, and the Free and Professional (Reviewer) edition gate is static inference only.
- Privilege ceiling: OS command execution as `uid=1001(collab) gid=1001(collab) groups=1001(collab)`, with an empty effective capability set, full read and write over `/usr/local/ccollab_server/**`. Root was **not** reached: the image contains no `sudo` binary and neither `/etc/sudoers` nor `/etc/sudoers.d`, ships no first-party setuid executable, and provides no designed path from an application administrator to the root account. No escalation was attempted and none is claimed.

## Impact

- **Post-authentication write becomes unauthenticated execution.** A single low-privilege account plants a Groovy Server Page in the webroot that any anonymous client - including a crawler, a scanner or any other unauthenticated party - will execute on request. The party who writes and the party who triggers need not be the same, and the chain crosses the authentication boundary in that direction.
- **Full command execution as the service account.** Verified by a marker template running `["id"].execute()` and returning `uid=1001(collab) gid=1001(collab) groups=1001(collab)` in an anonymous response body.
- **Every credential in the product is exposed.** Unsalted ASCII-MD5 password digests for all Collaborator accounts in `hsqldb/database.data`; the database superuser `sa` with an empty password at `conf/Catalina/localhost/ROOT.xml:33`; and source-control passwords, OAuth client secrets and licence user lists decryptable with the constant key embedded at `EncryptUtils.java:31-32`. Every configured SCM and identity-provider integration is compromised along with the product.
- **All review content is readable and writable**, and because `addZipFiles:982` performs no per-object authorisation on a caller-supplied `reviewId`, the write primitive is not confined to reviews the attacker created - other teams' review material can be written into independently of the webroot question.
- **Availability.** The service account owns the Tomcat tree, so application classes, deployment descriptors and the database file can be overwritten or deleted to terminate service.
- **Persistence for anyone who already has execution**, using the same primitive. Whether a planted template survives a restart is **not established**: the webroot is unpacked from the war at runtime and no restart was performed, so no claim is made in either direction.
- **Detection is weak by design of the responses.** HTTP 200 accompanies success, the blocked shape and the partially-failed shape alike, and the product's audit log records only a review creation and a file-addition line naming a version directory - never the entry name, the traversal or the webroot destination. Groovy compiles the template in memory, leaving no artifact in the work directory. The reliable indicator is a `.gsp` file under `webapps/ROOT` other than the single shipped template at `ROOT/jsp/views/json_tester.gsp`.
- **Bounded by the host.** The achieved identity is unprivileged inside the container, with no capability, no `sudo` and no setuid path, so the blast radius is the product and everything it holds rather than the underlying host.

## Mitigation

1. Canonicalise and containment-test every archive entry name against the destination directory, per entry and not once per archive, in both `DoorsFilesUploadService.java:77-84` and `SimulinkFilesUploadService.java:186-203`: resolve each name against a normalised base and reject any result that does not start with that base, or compare canonical paths. Implementing it once in the shared parent `HtmlBaseFilesUploadService` fixes both instances and any future dispatch site.
2. Reject dangerous entry names explicitly as defence in depth - parent-directory segments, absolute paths and backslash separators - and apply that rejection after `Strings.replaceSquareBracketsToRound`, not before, since the substitution currently runs ahead of the concatenation.
3. Move the review-content tree out of the webroot's traversal radius, so that `content-webserver` no longer resolves to a sibling of `webapps/ROOT` inside the Tomcat working directory. This removes the property that turns a content write into a code write.
4. Enforce an extension allowlist on extraction output, or a denylist covering `*.gsp`, `*.jsp`, `*.jspx`, `*.war`, `*.class` and `*.jar`, and align the two upload routes by applying to `ReviewService.addDoorsFiles` and `addSimulinkFiles` the same restricted-file-pattern discipline that `VersionContentUploadServlet:90-93` already applies.
5. Narrow the `*.gsp` mapping in the ROOT webapp's deployment descriptor: relocate templates under `WEB-INF`, bind the mapping to authenticated access, or remove it. This eliminates the execution half of the chain and reduces the defect to a file write inside the content tree.
6. Make `AuthTicketFilter` default-deny. It currently authenticates opportunistically at `:118`, forces a 401 only on the single two-operand condition at `:122`, and otherwise allows at `:128`; inverting that also closes the demonstrated bypasses of the exclusion pattern and the prefix test.
7. Fix the image packaging so every `VOLUME`-declared path is created and chowned to the service account at build time, as the database directory already is. This removes the inconsistency between two identically declared volumes and eliminates the only mechanism currently blocking the chain in the container shape - it is a correctness fix, not a mitigation.
8. Until a patch exists, operators should put file-integrity monitoring on the Tomcat webroot alerting on any new file under `webapps/ROOT` and any `.gsp` other than the shipped template; treat every account holder as able to reach the sink; egress-filter the service; and rotate all stored source-control, OAuth and directory credentials plus all Collaborator passwords on any instance where compromise is suspected. Alert on the JSON `code` field combined with a webroot change rather than on HTTP status, and monitor for the two-request shape - a multipart `POST /services/json/v1` naming `ReviewService.addDoorsFiles`, followed by an anonymous `GET` for a `.gsp` path that is not part of the shipped installation.
9. Add a regression test that builds an archive containing one entry whose name traverses out of a temporary destination, asserts that a containment `IOException` is raised **and** that no file appears outside the temporary directory, and repeats for both extractor instances and for absolute and backslash-separated names. The filesystem assertion matters more than the exception assertion: the verification observed a round where the response was an error and the write had already succeeded.

## PoC

`exploit/smartbear_collaborator_doors_upload_zip_slip_webroot_gsp_rce.py` - Python 3 standard library only, no local shell-out, archive assembled in memory. Obtains a login ticket, builds a randomly tagged marker archive, posts the batched `authenticate` plus `addDoorsFiles` command array as multipart, performs the anonymous GET, and reports the marker and evaluation evidence. `--control` repeats the identical request with the traversal entry removed and shows that no marker appears in the webroot, which is the negative control that attributes the escape to the entry name. `--host` defaults to `127.0.0.1`, the tool refuses to run without an explicit authorisation flag, the payload default is a non-destructive identity probe, and the marker is never deleted on the target - cleanup is printed as an instruction.

## Independence

This sink is not a re-published public issue. On the authoritative product axis, `virtualMatchString=cpe:2.3:a:smartbear:collaborator`, two records exist: CVE-2020-26118, a post-authentication Java deserialization in the Google Web Toolkit API of Collaborator Server through 13.3.13302 involving `UpdateMemento`, and CVE-2021-41657, a clickjacking issue in the web UI of CodeCollaborator 6.1.6102. Neither is a path-traversal root cause, neither touches archive extraction or a template-servlet mapping, and both are on different version lines. The former-product-name and variant CPE axes return zero records, and the GitHub Security Advisory database returns none. Keyword search is unusable as a primary axis for this product name: a search on it returns eleven records of which exactly one belongs to this product, the rest being an intercepting proxy, a source-code host and other unrelated software. The nearest public precedent is CVE-2024-7565, a directory traversal in the `unpackageAll` routine of a different product from the same vendor - same weakness class, same vendor, different product line, with shared code positively excluded: `unpackageAll` returns zero hits across the 4457-file corpus, as does `soapui|readyapi`, while controls over `ZipProcessor|unzip|copyFilesFromZip` return four and over `smartbear` return 4386. Two limits are stated: the search establishes absence of evidence within public indexes only, and exactly one build was exercised.
