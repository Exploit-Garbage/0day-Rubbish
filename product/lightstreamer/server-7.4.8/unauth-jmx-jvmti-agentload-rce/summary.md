# Lightstreamer Server 7.4.8 — Unauthenticated JMX `jvmtiAgentLoad` Native Code Execution

Advisory: https://0day-rubbish.com/blog/lightstreamer-unauth-jmx-jvmti-agentload-rce
Repository: https://github.com/Exploit-Garbage/0day-Rubbish
Contact: disclosure@0day-rubbish.com

## Summary

Lightstreamer Server 7.4.8 build 3506 exposes an embedded JMX inspection console derived from `jminix` at `/dashboard/jmxtree/`. In the configuration file inside the official distribution archive, `<jmxtree_enabled>` and `<dashboard><public>` are both shipped as `Y`, even though the comments beside them claim the default is `N`. With those values the console asks for no credentials; the only remaining check is that the request carries a `Referer` header matching the target host and port and the `/dashboard/` path, which any HTTP client forges with one flag. No authentication filter runs ahead of routing in the server's own HTTP stack.

An anonymous client may therefore invoke any MBean operation, choosing the domain, key properties, operation name, signature and arguments in a single request. `jvmtiAgentLoad` on `com.sun.management:type=DiagnosticCommand` makes the running JVM load a native agent library and execute its entry point inside the Lightstreamer process, with that process's authority; the library path and the options string both come from the request body, so the command is chosen at send time. Reaching that operation requires a double-encoded signature (`%255B` / `%253B`): Restlet 2.4.3 treats a literal `;` as a matrix-parameter separator, but `jminix` decodes the path a second time with `URLDecoder.decode`, so the exact signature `[Ljava.lang.String;` is reassembled after routing and matches the MBean's declared signature.

We verified `200` with `return code: 0` on both `curl` runs and the first Python proof-of-concept run, marker files recording `uid=0(root) gid=0(root)`, and `id` / `whoami` commands chosen by the HTTP client at send time and executed as `uid=0(root)`, reproduced by an independent re-analysis with its own agent and by an adversarial falsification pass in which five of six load-bearing claims held. The sixth did not, and it is the one real precondition: `jvmtiAgentLoad` takes a filesystem path and fetches nothing (`http://` and `file://` were both treated as literal strings), so the agent library must already be present, at a filesystem path the attacker specifies, before the request is sent. In our verification the library had been placed there beforehand over an authenticated root session on the research host, so what was proven unauthenticated is the request leg, not the delivery leg. We looked for a way to place it using only what this endpoint exposes and found none: the other unauthenticated file-writing diagnostic operations (heap dump, JVM log dump, and dumping JFR data via `jfrDump`) emit HPROF, log text and JFR rather than arbitrary ELF bytes, and the distribution exposes no HTTP upload endpoint an anonymous client could use. **The fully remote chain, payload delivery included, is therefore not demonstrated by this advisory** — that is the one load-bearing claim the adversarial falsification pass broke, and it is why the pure-remote figure is 8.1 rather than 9.8.

## CVSS Score

Dual-scored on the one documented delivery precondition, following the derivation in analysis section 12: the unauthenticated MBean-invocation primitive and the native-code-execution primitive behind it are remote on any unmodified installation, but the library they load must already sit at a filesystem path the attacker names, and this endpoint offers no way to put it there. Both figures are published rather than a single headline number, and every reading in analysis section 12 is reproduced below against its own vector. The scenarios named in the conditional readings are ways that precondition could be satisfied, taken from analysis section 12; none of them forms part of a remote chain demonstrated here.

- **Score**: 8.1 High — primary and conservative, for an attacker with network access only: the agent library must be delivered by means outside this endpoint
- **Vector**: CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H
- **CWE**: recorded by the research as CWE-306 (missing authentication for critical function), CWE-345 (insufficient verification of data authenticity — a `Referer` header as the sole authorisation decision), CWE-20 (two decoding stages over one path) and CWE-250 (execution with unnecessary privileges). CWE-1188 (insecure default initialisation of resource — shipped values contradicting the shipped documentation of those same values) is added by this advisory's own classification rather than carried from the research record
- **Class**: pre-authentication, network to native code execution inside the broker JVM
- **9.8 Critical — conditional, not the primary figure**: `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H` — shipped-default exposure where the precondition is already satisfied, that is a native shared object is already reachable at a filesystem path the attacker specifies (analysis section 12 lists a co-resident writer, an attacker who already holds local access on the target, and a companion write primitive as the ways it could be met); exploitation is then one deterministic HTTP request, with no race, no memory-corruption reliability question and no per-target guessing
- **7.8 High** — `CVSS:3.1/AV:L/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H` — analysis section 12's local-escalation reading of the same defect: a local user writes the library where the root-owned service process will load it. A scenario, not a path demonstrated in this advisory
- **7.5 High** — `CVSS:3.1/AV:N/AC:H/PR:L/UI:N/S:U/C:H/I:H/A:H` — operator hardened the shipped values (`<public>N</public>`, so valid dashboard credentials are required) while the delivery precondition still applies
- **9.1 Critical** — `CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:C/C:H/I:H/A:H` — the primary case re-read with Scope Changed, i.e. treating the host operating system as a distinct security realm
- **10.0 Critical** — `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H` — the conditional case re-read with Scope Changed

`Scope: Unchanged` is published as primary because the agent executes inside the Lightstreamer JVM with the authority that process already held, and no sandbox, container or trust boundary was crossed to obtain it; the two `S:C` figures are disclosed here so that the difference is visible rather than buried.

## Affected Products

- **Vendor**: Lightstreamer S.r.l. (Milan, Italy) — commercial Java real-time streaming and messaging broker, distributed as a Java `tar.gz` unpacked and started with `bin/unix-like/LS.sh start`. It pushes real-time data streams — financial quotes, news, sports results, collaborative-application state — to browser and mobile clients, and in customer deployments it sits in the communications path rather than beside it
- **Product and version verified**: Lightstreamer Server 7.4.8, build 3506, ENTERPRISE edition with a demonstration licence (zero-configuration start), together with JMS Extender 2.1.0, running on a JDK 17 runtime
- **The default-configuration claim is proven from artefacts, not from lab state**: the official distribution archive was extracted into a clean directory and its configuration diffed against the running instance. The `<dashboard>` block was byte-identical and carries `<jmxtree_enabled>Y</jmxtree_enabled>`, `<public>Y</public>` and `<available_on_all_servers>Y</available_on_all_servers>`. The only two differences were the listening port (the lab used `8181` in place of the shipped `8080`) and `<listening_interface>` — left commented out in the shipped file, so the shipped server binds every interface rather than a chosen one, and set to the loopback address in the lab
- **Other versions, editions and builds were not tested.** No larger affected set is claimed
- **Identifier status**: none assigned. The survey recorded during research found no prior published entries for Lightstreamer Server in the sources checked

## Impact

- **Execution context**: inside the Lightstreamer JVM as the service process, inheriting that process's full identity. In the verified deployment the process ran as `uid=0(root)`, so the executed commands ran as root; root is not claimed to be a factory-mandated identity — it is whatever account launched the service
- **Confidentiality: High** — the streaming server's configuration and anything on disk readable by the process. The product's own authentication model names a Metadata Adapter as one of its layers, so credentials configured for that adapter sit inside the same process and fall within its reach; whether adapter credential material, live process memory or in-flight stream data is in fact readable was not examined in this research, and those three reaches are inference from the execution context rather than observation
- **Integrity: High** — the process can modify its own configuration and adapters, tamper with streamed content and, as root in the verified deployment, modify the host
- **Availability: High** — the service can be terminated, its streams corrupted or the JVM destabilised, both by the loaded agent and by the other diagnostic operations reachable through the same unauthenticated endpoint (dump the heap, dump JVM logs, dump JFR data via `jfrDump`)
- **Persistence**: a loaded JVMTI agent would be expected to remain resident in the JVM for the process lifetime, although residency was not observed in this research. Logging behaviour around the invocation was not examined, so no claim is made about what it does or does not record
- **Blast radius**: a streaming broker commonly holds credentials toward upstream JMS brokers and downstream data sources, so a foothold there is a foothold on the systems it is integrated with

## Mitigation

1. Change the shipped defaults to match the documented defaults: ship `<dashboard><public>N</public>` so HTTP Basic authentication is enforced, and `<jmxtree_enabled>N</jmxtree_enabled>` so the JMX tree is opt-in — the current file states one thing in comments and does another in values (CWE-306, CWE-1188)
2. Stop treating `Referer` as an authentication decision; require a real server-side session or token for any administrative invocation (CWE-345)
3. Allow-list invocable MBean operations — a console permitting arbitrary invocation against `com.sun.management:type=DiagnosticCommand` is a code-execution feature, and `jvmtiAgentLoad` and equivalents should be unreachable from an HTTP-facing console regardless of authentication state
4. Resolve the double-decoding inconsistency so that exactly one component decodes the request path and downstream consumers receive already-decoded values (CWE-20)
5. Do not run the service as root; drop to a dedicated service account at startup or refuse to start as uid 0, and require an explicit `<listening_interface>` instead of binding every interface by default (CWE-250)
6. Operators, without a patch: set `<public>N</public>` with strong Basic credentials and `<jmxtree_enabled>N</jmxtree_enabled>`; bind the listener to a management interface and keep the administration port behind a VPN or mutually authenticated reverse proxy; run the server as an unprivileged dedicated user; monitor request logs for `POST /dashboard/jmxtree/` traffic carrying `%255B` or `%253B`, and treat a `200` response with `return code: 0` from an anonymous caller as a compromise indicator
