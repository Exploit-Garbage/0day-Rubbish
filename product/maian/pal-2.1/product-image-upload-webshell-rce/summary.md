# Maian Pal 2.1 - Unrestricted File Upload in the Administration Product Image Handler (CWE-434)

Advisory: https://0day-rubbish.com/blog/maian-pal-product-image-upload-webshell-rce
Repository: https://github.com/Exploit-Garbage/0day-Rubbish
Contact: disclosure@0day-rubbish.com

## Summary

Maian Pal is a commercially distributed, self-hosted PHP shopping-cart script from Maian Media (United Kingdom), oriented at PayPal checkout and shipped with an administration back-end that dispatches through `admin/index.php` into `control/_ajax.php`. In version 2.1 the product-image handling of the product create and update operations (`ajax-ops=add`, `ajax-ops=add-edit`) passes the multipart field `fm[ifile][]` to `products::pictures()` (`class.products.php:333` through `class.products.php:410`), which chooses the stored name from the client-supplied filename with a single ternary and applies no extension allow-list whatsoever; under the shipped `thumbcfg()` default `'rename' => 'no'` (`class.products.php:615`) the assignment at `class.products.php:372` reduces to `$picPath = $name`, so a `.php` extension reaches the disk intact. The object is written by `move_uploaded_file()` at `class.products.php:~390` into `content/products/<ID>/`, a directory inside the document root that our review of the shipped tree found to carry no Apache deny file and no handler restriction, while `admin/import/` in the same shipped version does carry a `Deny from all` rule and the product's attachment upload path does apply an extension allow-list into a deny-protected directory. Because the front-controller rewrite rule claims only paths that do not exist on disk (`RewriteCond !-f` guarding `RewriteRule ^([^?]*) index.php?_msw_=$1 [L,QSA]`), an existing `.php` object is handed straight to the PHP handler, and requesting it with a query string executes it - observed as `uid=33(www-data)`, the Apache/PHP service account, which is the privilege ceiling of this finding. The ordering inside the handler makes the failure path worse rather than safer: `move_uploaded_file()` runs before any thumbnail inspection, and `thumbnail()`'s failed `getimagesize()` falls through its `switch` to a suppressed `@copy()`, so a non-image upload leaves two objects on the served directory (the original plus a `tmb_`-prefixed copy), deletes neither, and still reports success. Reaching the sink requires a valid administrator session and the session CSRF token; there are no factory credentials because the installer forces them to be set, this is not a default-credential issue, and no unauthenticated route to the sink was found.

- **Component**: the administration product create / update path - `control/_ajax.php:686` (cases `add` / `add-edit`) -> `control/_ajax.php:720` (`$fm['ifile']`) -> `control/_ajax.php:734` (`$PRD->add($fm)`) -> `class.products.php:299` (`products::add()`) -> `class.products.php:333` (`pictures()`), storing into `content/products/<ID>/` and exposing the result at `GET /content/products/<ID>/<filename>`
- **Sink and source**: the sink is `move_uploaded_file($temp, $picFldr . '/' . $picPath)` at `class.products.php:~390`, with execution following as the web server service account on the subsequent `GET /content/products/<ID>/<filename>?cmd=<command>`; the source is `$_FILES['fm']['name']['ifile'][$i]` and `$_FILES['fm']['tmp_name']['ifile'][$i]`, assembled at `control/_ajax.php:720` from an ordinary `multipart/form-data` POST in which the filename component of the part is entirely client-controlled
- **Sanitization**: nothing on the path constrains the file type. `strtolower()` appears only in the non-default `rename='yes'` branch and is cosmetic; the CSRF comparison at `control/_ajax.php:17` and `mswPerms()` (defined at `functions.php:85`, called at `control/_ajax.php:85`) authenticate the operation rather than its parameters; `getimagesize()` inside `thumbnail()` runs after the write and only selects a thumbnail strategy, falling back to `@copy()` when it fails. There is no extension allow-list or deny-list, no `finfo`/MIME verification, no re-encoding, no server-generated filename with a type-derived extension, and no rollback of the write on failed validation

## CVSS Score

- **Score**: 7.2 High (CVSS 3.1, AV:N/AC:L/PR:H/UI:N/S:U/C:H/I:H/A:H) - an administrator-authenticated unrestricted upload that yields arbitrary command execution as the web server service account, entirely inside the application's own trust domain
- `AV:N` - the sink is reached over the ordinary HTTP(S) listener of a web application; the product exposes no separate management port, no RPC endpoint and no background listener, and nothing in the chain depends on source address, user agent or session age beyond validity
- `AC:L` - one POST creates the object and one GET executes it, so there is no race window, no multi-step state to prepare and no unusual configuration requirement. The chain depends only on shipped product defaults (`thumbcfg()` `'rename' => 'no'`, no deny file in `content/products/`), and the licence restriction (`RESTR_PRODUCTS = 50`) does not obstruct the first product create
- `PR:H` - only an authenticated administrator session was demonstrated. The credential pair is the one the installer provisions (`LG_USER` / `LG_PASS` in `control/_cfg.php`), `mswPerms()` gates every administration operation except `login` and `logout`, and no graduated back-end role was shown to reach `ajax-ops=add`. The `PR:H` weight under Scope Unchanged is precisely what separates this rating from the conditional reading below
- `UI:N` - no victim browser or user action is involved; the attacker authenticates with their own credentials and there is no forgery step that would require an administrator to visit a page
- `C:H` - the achieved identity reads the application's own configuration, since the web server user must read `control/_cfg.php` to function: database credentials, `SECRET_KEY` and the administrator secret the login path transforms. The customer and order tables (32 installed tables, including `shop_accounts`) and any stored payment-gateway, PayPal, mail or third-party API credential are equally readable
- `I:H` - the same identity writes wherever the service account can write, which includes the web root (persistence, defacement, additional objects in theme directories) and, through the application's own database credential, prices, stock levels, discount rules and order contents. Authorisation controls are entirely absent for that identity, and financial rewrites are invisible in the HTTP access log because they travel over the application's own database connection
- `A:H` - storefront content, product images, configuration files and the database itself can be deleted or corrupted with the application's own credential, taking the shop offline and destroying its catalogue. Availability of the whole service is at that identity's discretion
- **Scope**: Unchanged. The vulnerable component is the administration back-end of the cart application, and the impacted resources are that application's own files, its own database (reached with the very credentials the application itself holds) and the operating-system context of the web server process it runs inside. The achieved identity is the same service account the application always ran as, on the same host, and nothing outside its reach before the upload came into reach afterwards. The Scope-Changed variant AV:N/AC:L/PR:H/UI:N/S:C/C:H/I:H/A:H = 9.1 is therefore rejected: publishing it would require a database-server compromise independent of the application's credentials, a container escape or a distinct host, and none of those was demonstrated
- **CWE**: CWE-434 (Unrestricted Upload of File with Dangerous Type) primary; CWE-94 and CWE-693 contributing - the stored object is subsequently interpreted as code, and the served upload directory lacks the execution restriction that equivalent directories in the same product carry; CWE-78 describes what the demonstration payload does once it runs and is not scored separately. This is not CWE-22, because the demonstrated chain needs no traversal, and not CWE-798 or CWE-259, because there are no hard-coded or default credentials and the sample configuration ships a placeholder rather than a usable secret
- No numeric base score was recorded against this vector before publication, so there is no recorded figure that could disagree with it; the vector and score published here were derived for this advisory with the CVSS 3.1 base arithmetic shown in full in the deep-dive, and were re-checked against an independent implementation of that formula
- **Conditional reading, labelled as such and not the headline**: the dispatcher exposes `users`, `users-edit`, `permissions` and `permissions-edit`, so the product may model back-end accounts narrower than the single installer-provisioned administrator. `mswPerms()` was established in our review only as an authentication gate over the dispatch, not as a per-operation authorization matrix, and no principal short of full administrator was demonstrated to reach `ajax-ops=add`. If the vendor confirms that a restricted back-end account can create or update products, then that account is the least-privileged principal reaching the sink and the rating becomes AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H = 8.8. It is not published as the headline because doing so would assert a privilege model that was not observed
- **Rejected - unauthenticated**: AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H = 9.8 would be the tempting headline for a public-facing shopping cart, and it is false here. The storefront dispatcher's 56 unauthenticated AJAX operations contain no file-upload, command-execution, code-evaluation or deserialization primitive - only `include()` of language and class files - the administration login was reviewed on six specific bypass axes with no success, and the product ships no factory credential and no usable `SECRET_KEY`
- **Rejected - elevated complexity**: AV:N/AC:H/PR:H/UI:N/S:U/C:H/I:H/A:H = 6.6 is printed only so that the rejection is auditable; there is no race, no ordering constraint beyond one POST and one GET, and no requirement that the target be in an unusual state
- **Rejected - user interaction**: AV:N/AC:L/PR:H/UI:R/S:U/C:H/I:H/A:H = 6.8 is printed for auditability only; no victim action is required at any point in the chain
- Contributing weaknesses are reported but deliberately not scored into this vector: the single-round SHA-1 `mswEnc()` credential transform, loose `==` comparisons on hash and token strings, the absence of any enforced rotation of the installer-provisioned secret, and the inconsistency between upload handlers inside one shipped version. None of them lowers the privilege required to reach the sink and none of them raises the impact of the upload once it is reached

## Affected Products

- Maian Pal, version 2.1, from Maian Media (United Kingdom); commercially distributed as a self-hosted PHP script archive with an administration back-end and a storefront dispatcher (`control/system/_ajax.php`)
- Affected component: the product-image upload handler `products::pictures()` (`class.products.php:333` through `class.products.php:410`), reached from the administration dispatcher cases `add` and `add-edit`, together with the served destination directory `content/products/<ID>/` that carries no execution restriction
- Runtime stack: PHP 8.3 on Apache with `mod_rewrite`, MySQL for storage, 727 plain unobfuscated `.php` files in the shipped tree, administration entry point `admin/index.php` dispatching to `control/_ajax.php`
- Only this version was tested. Version 2.1 is the only version obtained, reviewed and executed; no other version, edition or bundle is claimed, and no claim is made about any other product from this developer
- Verification method and its boundary: the chain was verified dynamically against a containerised instance built from the shipped 2.1 archive - upstream `php:8.3-apache` image with `mysqli` and `gd`, a separate MySQL container on a private container network, a listener bound to loopback only, Apache with `mod_rewrite` enabled and `AllowOverride All`, `session.save_path` on a writable temporary directory, the installer run to completion (32 tables created) and removed afterwards. `AllowOverride All` is a setting we chose, and it is the setting under which the product's own shipped Apache deny files function, so it reproduces rather than defeats the intended protection model; the loopback binding is a safety property of our host and does not affect the chain, which depends on no source address. Not verified: any `nginx` or PHP-FPM deployment, any IIS or Windows deployment, the `rename='yes'` configuration (argued from the assignment expression only), extensions other than `.php`, case variants of the extension, the storefront download operation's path handling, the un-normalised filename concatenation, the `backup` / `restore` / `data-import` operations, and any privilege escalation beyond the service account
- Privilege ceiling: web execution as the PHP/Apache service account, observed as `uid=33(www-data) gid=33(www-data) groups=33(www-data)` in three independent reproductions, plus a marker file written to an absolute path outside the document root and read back afterwards. Not reached: root, the host, the database server as an independent component, any container escape and any other host. On a distribution-packaged install the equivalent account is commonly `www-data`, `apache`, `httpd`, `nginx` or `www`; what is constant is that it is the application's service account
- Authentication precondition: a valid administrator session plus the session CSRF token delivered as `<meta name="x-header-csrf" content="...">` and returned as the `X-CSRF-Token` header. There are no factory credentials in Maian Pal 2.1 The CSRF token is validated on this specific operation: the gate at `control/_ajax.php:17` sits structurally ahead of the case dispatch at `control/_ajax.php:686`, and the token was supplied and accepted on the login, the category create and the product create alike. The inverse experiment - the same product create with the header omitted - was not run, so enforcement on `ajax-ops=add` rests on that code position plus a consistently supplied token rather than on an observed rejection. Holding credentials implies holding the token, so it adds no privilege barrier. - the installer forces `LG_USER`, `LG_PASS` and `SECRET_KEY` to be set, and `control/_cfg-sample.php:62` ships only the placeholder text `Your secret key value goes here` - and there is no administrator password-reset flow, since changing the credential means editing `control/_cfg.php`

## Impact

- Configuration and credentials become readable: the web server user must read `control/_cfg.php` to function, so it yields the database credentials, the `SECRET_KEY` and the administrator credential material the login path transforms. Everything the login gate protects is obtainable directly from disk, together with any other secret the application stores - payment-gateway keys, PayPal configuration, mail credentials, third-party API keys
- Customer and order data become readable and writable: with the database credentials from `control/_cfg.php` the 32 installed tables are open, including customer accounts in `shop_accounts`, orders and addresses, so the confidentiality impact falls on the store's customers and not only on its operator
- Financial integrity becomes writable: prices, stock levels, discount rules and order contents are database rows, so a silent price or order rewrite is an integrity impact with direct financial consequence - and it is invisible in the HTTP access log because it happens over the application's own database connection
- Persistence and defacement in the web root: the webshell is an ordinary file in a directory the application serves, so it survives session expiry, service restarts, administrator logouts and application updates. Additional objects can be placed in theme directories or reached by modifying an existing storefront template, and a cleanup that removes only the obviously named object leaves the `tmb_`-prefixed sibling behind - deleting the product row through the interface is not guaranteed to remove the image directory at all
- Availability is destroyable: storefront content, product images and configuration files can be deleted or corrupted, and the database can be damaged with the application's own credential, taking the shop down and losing its catalogue
- A foothold on the host: the service account's local view - environment variables, readable system files, other applications reachable on localhost, outbound network access from the host - is available for further activity. We pursued none of this and make no claim that it leads anywhere in a given deployment
- Detection is genuinely difficult because the traffic is legitimate. The highest-value indicator is a `GET /content/products/<ID>/<name>.php` - a script-extension request under a product image directory, almost never legitimate, and stronger still with a query string such as `?cmd=` - preceded by one `POST /admin/index.php?ajax-ops=add` whose request line is indistinguishable from a normal product create. On the filesystem, look for non-image extensions inside `content/products/*/` and especially for paired objects where a `tmb_`-prefixed file shares its original's non-image extension; both must be removed. The application audit trail is the weakest signal of the four, since both operations report `{"status":"ok"}` and no suspicious filename is recorded
- The ceiling is stated as clearly as the impact: no root, no host compromise, no database-server compromise beyond what the application's own credentials grant, no container escape and no evidence about other hosts. The demonstrated outcome is arbitrary command execution as the web server service account, and this advisory does not exceed it

## Mitigation

1. Close the handler, which is the root-cause half that lets the file be written: in `products::pictures()` resolve the extension from the client filename, normalise its case and compare it against a fixed permitted set (`jpg`, `jpeg`, `png`, `gif`, `webp`) before anything is written, rejecting everything else with a validation error. Apply the same shared validator to every file-accepting handler in the product so the attachment path and the product path cannot drift apart again. The existing `rename='yes'` option is not a substitute - that branch still takes the extension from `strrchr($name, '.')`, so a `.php` upload under it produces a server-named file that is still executable
2. Close the directory, which is the second root-cause half and is required in addition: make the served upload tree non-executing at server-configuration level rather than by `.htaccess` alone (vhost `FilesMatch` denial with `SetHandler none`, `php_admin_flag engine off`, `RemoveHandler` / `RemoveType` for the script extensions, `Options -ExecCGI -Indexes`), and document the equivalent `nginx` `location` rule. A patch addressing only one half leaves the other standing
3. Stop trusting the client filename: derive the stored name entirely server-side from a random or sequential token plus a fixed extension chosen from the validated type, never from the submitted string, and normalise away path separators - or better, never interpolate the client string into a filesystem path at all
4. Move uploads out of the served tree, which removes the second half of the root cause by construction rather than by configuration: store product images outside the document root or on separate storage and serve them through a download operation that cannot execute what it reads
5. Validate before writing and roll back on failure: move `move_uploaded_file()` to after `getimagesize()` or a `finfo` check succeeds, delete the object when any later step fails, and replace the suppressed `@copy()` fallback in `thumbnail()` with an explicit error plus cleanup so that an object whose type could not be determined is never duplicated
6. Reduce the credential blast radius, treating this as a contributing weakness rather than part of the upload vector: replace the single-round SHA-1 `mswEnc()` transform with `password_hash()` / `PASSWORD_ARGON2ID` storing a hash instead of a plaintext constant, compare with `hash_equals()` and strict equality, keep `SECRET_KEY` for session and cookie signing only, and - given that the whole product surface is one administrator credential away from operating-system command execution - add a second factor to the back-end login, with guidance or an enforced step for rotating the administrator secret and network-restricting the back-end
7. Ship regression tests for both halves: a behaviour test asserting that a `.php` upload through the product-image operation is never served as code (no execution marker in the response body, status 403 or 404), and a packaging test asserting that every writable directory under the document root able to receive uploads carries an execution restriction. The second test is the one that generalises, because it asserts the consistency property this advisory is really about - a newly added upload directory then cannot ship unprotected
8. Operator-side, and the highest-value action that needs no vendor patch: add the execution restriction from item 2 to your own web server configuration for `content/products/` and, for consistency, `admin/attachments/`, `admin/import/` and any theme cache directory; confirm that `AllowOverride` actually applies before relying on any deny file the product ships, and enforce the rule in the vhost where possible; add an edge rule (WAF or reverse proxy) rejecting script extensions under product-content paths, matched on `^/content/products/.*\.ph(p[3457]?|t|ml|ar)$` and logged as a security event; and restrict reachability of `admin/index.php` by source-IP allow-list, authenticating reverse proxy or VPN so that credential possession is not the only barrier. Run the web worker with the least privilege available - a dedicated service user, a read-only document root where the layout permits, and upload directories owned separately from the code
9. Operator-side response and hygiene: inventory the product image directories now for non-image files including `tmb_`-prefixed objects and remove both halves of any pair; audit product and category rows created outside your own activity, remembering that deleting them does not necessarily remove the image directory; after any suspected abuse treat `control/_cfg.php` contents (administrator secret, `SECRET_KEY`, database credentials) and every stored payment-gateway or API credential as disclosed and rotate all of them, assuming the database contents were readable; monitor for the detection pattern in the Impact section; and do not assume the `rename` thumbnail option protects you
