# Titan MFT Server 26.0.0 - Unauthenticated First-Run Administrator Setup Chained to Job Post-Command Injection in the WebAdmin Blazor Application (CWE-306, CWE-78)

Advisory: https://0day-rubbish.com/blog/southriver-titan-mft-firstrun-admin-setup-job-command-injection
Repository: https://github.com/Exploit-Garbage/0day-Rubbish
Contact: disclosure@0day-rubbish.com

## Summary

Titan MFT Server is a commercial managed file transfer server from South River Technologies (Annapolis, Maryland, United States); version 26.0.0.364 of the NextGen generation runs as a single .NET 8 process, `titanmft.exe`, registered as the Windows service `SrtTitanMFTServerService` under LocalSystem, serving a Blazor Server administration application on `0.0.0.0:47443` over TLS and driving file transfers with EF Core over SQLite (`mftlasdb.db`, a domain `mftdb` database and a Quartz scheduler database). A default installation contains no administrator accounts, so the user table `mftlasdb.nxUserParams` holds zero rows, and in that state `/Login` renders an "Initial Admin User Setup" screen to any client that can reach the listener — gated only by `RunWizard = !nxUserParams.AdminUserExists() && !CreateAdminAtConsole` at `MxSvrParams.cs:518-520`, with no bootstrap ticket, no CAPTCHA, no first-boot token, no localhost restriction, and `IpAccess Enabled:0` (CWE-306). Submitting that screen calls `AppState.CreateAdminUser` followed by `AppState.Login` inside the in-process circuit and lands the anonymous client in the management console at `/SvrHome/<guid>/<guid>`. The attacker then creates a job and writes its post-transfer command field `Execute After File Transfer Task`, which is persisted verbatim into `nxJobs.document.PostCommandText` and, when the job runs, is passed by `MxUtilSvrJobHandler.RunCustomProcessAsync` (`MxUtilSvrJobHandler.cs:991`, reached from the predicate at `:970` via the call site at `:979-982`) to process creation with `UseShellExecute = false`, a plain `Arguments` string, no allow-list and a `cmd`-prefix special case that concatenates `"/c " + command.Substring(3).Trim()` (CWE-78). The child therefore inherits the service token, and the injected `cmd /c whoami > <marker>` wrote a 21-byte file containing `nt authority\system`. This is a first-run window, not a permanent unauthenticated condition: it opens when installation completes and closes the moment the first administrator exists, after which `/Login` renders a credential form instead and this chain's first half has no route.

- **Component**: WebAdmin Blazor Server administration application (`/Login` first-run setup screen, in-process circuit, DevExpress `dxbl-*` component tree) chained to the transfer engine's job post-command handler in `Srt.NextGen.ServerCore`
- **Sink and source**: `MxUtilSvrJobHandler.RunCustomProcessAsync` at `MxUtilSvrJobHandler.cs:991` (a second pass over the same decompilation records `:996`), reached only when the predicate at `:970` finds a non-blank `PostCommandText` and either a successful transfer or the on-failure flag; source is the unauthenticated setup form on `/Login` plus the authenticated job-editor field `Execute After File Transfer Task`, both carried over the Blazor circuit
- **Sanitization**: none on the command field. `NxDecryptAPI` (AES-ECB static key, `StringExtensions.cs:1008`) is optional transport obfuscation of credentials and returns its input unchanged without the encryption prefix; the editor's connector-presence check is a client-side usability guard, satisfied by choosing the built-in local filesystem connector; and zero `[Authorize]` attributes exist anywhere in the 1,880 decompiled `ServerCore` files

## Affected Products

- **Product**: Titan MFT Server 26.0.0.364 (NextGen generation), from South River Technologies (United States, Annapolis, Maryland)
- **Also affected**: Titan MFT Server 26.0.0.348, installer artifact 312,248,120 bytes; the first-run half was confirmed dynamically on that build and the injection tail rests on a shared code base, which is a structural argument rather than a separate replay
- **Affected component**: the WebAdmin Blazor Server administration application on `0.0.0.0:47443` (setup screen on `/Login`, console routes `/SvrHome/<guid>/<guid>` and `/SvrNodeJobs/<domain>/<node>/<guid>`) plus the job post-command path in `Srt.NextGen.ServerCore`
- **Runtime stack**: .NET 8 ASP.NET Core with Blazor Server (DevExpress `dxbl` component tree, in-process circuit), EF Core over SQLite in WAL mode (`mftlasdb.db`, `mftdb<domain-guid>.db`, matching `-Quartz.db`), one `titanmft.exe` process as LocalSystem over Kestrel, `nxcli` management client as .NET 9 NativeAOT, BitRock unattended installer (384,912,064 bytes); `Srt.NextGen.LegacyApi.dll` is NativeAOT with no managed metadata and exposes `CreateProcessAsUserW`/`CreateProcessW` imports
- **Only these builds were tested.** No other version, edition or family product (Titan FTP Server, WebDrive, the older 2.x generation) is claimed, and no cloud-shaped installation was sampled, so the `CreateAdminAtConsole` branch is unestablished rather than exempt
- **Verification method and boundary**: full-chain dynamic verification on a Windows host in our lab with a fresh default installation, driven over HTTP and the Blazor circuit by a headless Chromium-family browser under the DevTools protocol, with Python standard library tooling only. Three limits bound it: the first-run window was re-opened by an authorised local database reset (deleting administrator rows and restarting the service), because an earlier pass had completed setup; all traffic stayed on loopback with remote access firewalled off; and the second build's injection tail was not replayed. Nothing here characterises a specific live production installation
- **Privilege ceiling**: `nt authority\system` was reached and proven by marker content (21 bytes, `whoami` output, modification time 76 ms after the job-completion timestamp the product recorded). Beyond the host nothing was attempted: no domain compromise, no partner-system access, no persistence, no lateral movement and no destructive action was performed or measured
- **Independence**: not a re-published public issue. This vendor's published history is nine older-generation identifiers (the 45685-45690 series, 44685, 27744 and 45645) plus one installation-period identifier, `CVE-2022-34006`; all are post-authentication or installation-time and all sit in the superseded 2.x code base; none is a first-run-window issue. A circulated attribution of `CVE-2019-13358` to this vendor was checked and disproved. Five root-cause fingerprints (`PostCommandText`, `CreateAdmin`, `first-run wizard`/`Initial Admin User`, `RunCustomProcess`, `South River`/Titan) returned zero hits across the 208 product directories in our own prior-research corpus, which contained no MFT-genre entry at all
- **Identifier**: none assigned at the time of writing

## Impact

- **Complete compromise of the MFT host**: LocalSystem on the Windows server carrying the product, which permits creating accounts, installing services, writing to startup locations and reading host credential stores
- **Every trading partner's exchange credentials**: connector configurations, SFTP/FTPS/WebDAV account material and SSH and PGP key material live in the administration and domain databases, so a single host compromise becomes the compromise of every exchange relationship the host participates in — with parties who have no visibility into the incident
- **Silent read and tamper over transfers**: connector source and destination directories are readable and writable, permitting interception of in-transit files, substitution of content presented to partners, and removal of evidence
- **Transfer configuration control**: jobs, schedules, connector paths, notifications and audit settings can be rewritten, allowing a recurring partner transfer to be redirected without any partner-visible change
- **Availability of scheduled transfers**: stopping the service, disabling jobs, corrupting the SQLite databases or filling the connector volume halts every scheduled exchange, which for agreements with delivery windows is a business-continuity event
- **Exposure is a race with deployment, not a permanent condition**: the window opens at installation completion and closes at first-administrator creation. Its length is deployment-dependent — whether installation is scripted unattended, whether setup is deferred, whether the listener is published before configuration — and was not measured
- **Detection is anomaly-based, not signature-based**: every step is a documented administrative action, so no failed logins, injection payloads or exploitation signatures appear. The high-signal indicators are administrator rows created outside change control, the product's own `Post Command: <text>` log line, any child process of `titanmft.exe`, and jobs whose source and destination are both local directories while transferring nothing
- **Discovery is easy for an attacker**: the setup screen renders for any client, and a separately reported pre-authorised `ServerParams` read family returns the window-running flag to unauthenticated callers, so exposed installations can be enumerated at scale

## Mitigation

1. **Move initial-administrator creation off the network face** (root cause): perform it in the installer's console step, or require a one-shot bootstrap token generated at install time — printed to the installer transcript or written to a host-local file with a restrictive ACL — that is single-use and expiring. The `CreateAdminAtConsole` branch already exists for cloud-shaped deployments and is the natural home for this on all deployments
2. **Do not let the network listener start before setup is complete**, or bind it to loopback and the management interface until an administrator exists; this removes the deployment race entirely and does not depend on operator timing
3. **Constrain the command field**: construct the child process with `ProcessStartInfo.ArgumentList` instead of a single `Arguments` string, remove the `cmd`-prefix special case that reconstitutes shell semantics, enforce an allow-list of executables, reject `& | < > ` % ^ ( )` and newlines unless an explicit per-deployment switch enables them, and validate the working directory against the job's connector paths. Apply the same treatment to the pre-transfer command sibling
4. **Separate the execution identity**: do not run the transfer engine, and therefore post-commands, as LocalSystem. Use a virtual service account or a per-job token granted only the connector paths; `CreateProcessAsUserW` already appears in the shipped legacy shim, so the plumbing exists
5. **Stop leaking window state and internals**: remove the window-running flag and any administrator-exists differential from unauthenticated responses (the pre-authorised `ServerParams` family currently discloses both), and return a bare 400 instead of a .NET stack trace when legacy model binding fails
6. **Validate the predicate itself**: gate initial-administrator creation on a channel binding rather than on a row count, so that even a deferred deployment cannot be completed by a remote client
7. **Ship regression tests**: (i) with zero rows in the user table, a network request to the setup route must not create a user; (ii) a post-command of `cmd /c whoami > %TEMP%\x` must produce no file; (iii) the documented supported configuration must not run the service as LocalSystem; (iv) `ServerParams` must never return window state to an unauthenticated caller
8. **Operator, until a patch exists**: treat "installed but not configured" as an open exposure; complete first-time setup from the console in the same change window as installation; block inbound TCP 47443 (and 37443, 8080, 21, 80, 443 as applicable) at the host firewall or upstream until an administrator exists, and do not rely on the product's IP-restriction feature being enabled
9. **Operator, verification and containment**: put the administration listener behind an authenticating reverse proxy or VPN; confirm the window is closed by loading `/Login` in a browser and checking for a credential form rather than the setup screen (a plain HTTP fetch returns only the 3,869-byte Blazor host shell and will produce a false negative); re-check after any administrator deletion, restore or re-image; audit every job with a non-empty `PostCommandText`; and if the window was open on a reachable listener at any point, treat the installation as potentially compromised — audit the administrator list, review connector credentials and rotate partner credentials and key material as the risk assessment warrants
