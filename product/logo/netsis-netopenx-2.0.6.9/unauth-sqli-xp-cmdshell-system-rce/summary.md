# Logo Netsis NetOpenX REST 2.0.6.9 — Unauthenticated SQL Injection to xp_cmdshell SYSTEM RCE

Advisory: https://0day-rubbish.com/blog/netsis-netopenx-unauth-sqli-xp-cmdshell-rce
Repository: https://github.com/Exploit-Garbage/0day-Rubbish
Contact: disclosure@0day-rubbish.com

## Summary

NetOpenX REST, also distributed as Netsis Nox REST, is the REST API gateway of Netsis, the enterprise ERP suite from Logo, a Turkish enterprise software vendor, and it sits inside financial and accounting infrastructure as the integration point through which other applications reach the ERP's financial data and product registry store. Version 2.0.6.9 contains an unauthenticated SQL injection in its OAuth 2.0 token endpoint.

A single unauthenticated `POST /api/v2/token`, carrying no client credentials and no user credentials, supplies a form field named `idmuserid` that is copied verbatim into a login session object and concatenated raw into a SQL statement executed against the ERP database by `ServiceManager.GetIdmUserLastSessionInfo`. That call is issued before `OAuthManager.LogIn`, the method that actually validates the supplied username and password, so no valid user, token or client secret is required; the endpoint still answers HTTP 400 because the credential check fails afterwards, by which time the injected batch has already been committed. Three properties make this materially worse than an ordinary injection bug: the pipeline registers no global authorization filter, so every route lacking a per-action `[Authorize]` attribute is anonymously reachable; the token endpoint is an OWIN middleware route on which action filters never apply; and the shipped SQL fragment blacklist is inert, its visitor overrides never recording an invalid fragment.

The backend is SQL Server, so a semicolon yields a stacked batch and the same request runs `sp_configure` to enable `xp_cmdshell` and then executes an operating system command. The sink swallows all exceptions and returns null, so the injection is blind at the HTTP layer only.

Verification did not attack a stock installed product across a network. A complete Netsis ERP deployment was not achievable in the lab, so the chain was driven against a reconstruction of the product pipeline: the product's real OWIN startup, OAuth configuration, Web API configuration and authorization-server provider, hosted through `WebApp.Start<Startup>` in a self-compiled console host listening on loopback only, against a real SQL Server Express instance whose NETSIS login held sysadmin, with exactly one method body — `ServiceManager.GetConnectionString` — rewritten by a Mono.Cecil IL patch to clear a commercial licensing gate that is not a security boundary. The sink `GetIdmUserLastSessionInfo`, the authentication logic, the routing table, the OAuth provider and the SQL concatenation were all left as unmodified product code; the full harness inventory, and what is inferred rather than verified, is stated under Affected Products. From a clean slate with `xp_cmdshell` disabled and the marker file removed, a baseline and a `WAITFOR DELAY` request separated by roughly five seconds timed the sink, one request left `xp_cmdshell` reading as enabled in use afterwards and wrote a marker, and `whoami` returned `nt authority\system`: the injection enabled its own escalation path. Four independent runs, all against this reconstruction over loopback, across two harnesses plus the reference script agreed, an independent re-derivation from the decompiled sources reproduced the chain, and an adversarial falsification review across six properties refuted none of them.

## CVSS Score

9.8 is the figure recorded for this finding, and it describes only the tier in which the service's SQL login holds sysadmin, as it did in the verified environment. It is not a claim that command execution is available on every deployment, and it must not be read as a bare score standing on its own: the disclosure-tier lower bound and the stricter attack-complexity judgement belong in the public record alongside it rather than in a footnote, each against its own vector.

- **Score**: 9.8 Critical — recorded headline figure, conditional on the command-execution tier, i.e. the service's SQL login holding sysadmin
- **Vector**: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H
- **CWE**: CWE-89 (improper neutralization of special elements used in an SQL command), CWE-306 (missing authentication for critical function), CWE-78 (improper neutralization of special elements used in an OS command)
- **Class**: pre-authentication, network to operating-system command execution on the ERP database host
- **8.1 High** — `CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H` — the same impact set under a stricter attack-complexity judgement that treats the sysadmin property of the service login, a deployment characteristic outside the attacker's control, as a condition of successful command execution. Disclosed so readers who prefer that reading can apply it without reinterpreting the primary score; analysis section 12 retains `AC:L` because the single request needs no timing precision, no race, no man-in-the-middle position, no prior reconnaissance and no victim action
- **7.5 High** — `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N` — conservative lower bound where the service login is not sysadmin: the same request still yields unauthenticated blind SQL injection with data disclosure but no operating-system access
- **9.1 High — rejected, not restated as a verified score**: the research notes accompanying this finding estimated the reduced tier at approximately 9.1, but that figure carries no vector and is not reproducible from a disclosure-only impact set. The notes record no vector for that estimate and no enumeration or calculator search was performed to derive one. Under CVSS 3.1 `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N` does reach that figure, and it does so by silently assuming high integrity impact that a read-only characterisation does not support; no claim is made that it is the only vector reaching that figure, only that with a network vector, no privileges and no user interaction, reaching it requires an impact component beyond read-only confidentiality, which a disclosure tier does not establish. A non-sysadmin login that nonetheless holds write permission over the ERP schema would legitimately score toward that figure; that configuration was not verified

## Affected Products

- **Vendor**: Logo (Türkiye), enterprise software; **product**: Netsis ERP — NetOpenX REST API gateway
- **Version verified**: 2.0.6.9, delivered as a 63 MB `NetsisNoxRestSetup.exe` bootstrapper installing 84 assemblies under MSI hashed file names. Runtime stack: ASP.NET Web API hosted on an OWIN Katana `HttpListener`, bearer-token authentication via Microsoft.Owin.Security.OAuth, data access through System.Data.SqlClient against SQL Server, with Oracle also supported as a backend
- **Vulnerable assemblies**: NetOpenX.Rest.Service (controllers, `ServiceManager`, the OAuth authorization server provider, configuration registration) and NetOpenX.Rest.Core (`CommonExtention`, `JLogin`, `OAuthManager`, `QueryBlackListHelper`)
- **Verified on a reconstruction of the product pipeline, not on a stock installation reached over a network.** What was dynamic: the real OWIN `Startup.Configuration`, `OAuthConfig`, `WebApiConfig` and `CustomizedAuthorizationServerProvider` hosted through `WebApp.Start<Startup>` in a self-compiled console host bound to loopback address 127.0.0.1 port 8977 only; 40 assemblies renamed from their MSI hashed names to simple names; 24 binding redirects; a real SQL Server Express instance with a NETSIS database and a minimal NETSISREGISTRY table, Windows-only authentication, and a connected identity holding sysadmin. What was patched: exactly one method body, `ServiceManager.GetConnectionString`, rewritten with Mono.Cecil — 30 instructions replaced by a load of a fixed connection string followed by a return — to satisfy a commercial licensing gate that is not a security boundary. What stayed unmodified product code: the sink `GetIdmUserLastSessionInfo`, the authentication logic, the routing table, the OAuth provider and the SQL concatenation. What is inferred rather than verified: that a complete stock ERP deployment, with its licensed COM-produced connection string, single sign-on and license server, behaves identically; that configuration was never assembled and never exercised
- **The injection itself has no precondition.** The judgement that it is present and reachable in every deployment of this build, independent of database privileges, rests on two things and no more: static analysis of the raw-concatenation sink, in which nothing between the attacker-controlled form field and the concatenated command branches on database privileges or on any privilege-dependent configuration, and the verification harness, in which the sink fired on every run. Real deployments were not sampled, so it is a conclusion about the code path rather than a survey of installed systems. The elevation tier depends on the privilege level of the service login. our research notes assert that Netsis ERP deployments commonly run the NETSIS SQL user as dbo or sysadmin, but those notes cite no document, no artifact and no verification for the assertion, and this research did not verify it. The shipping connection string could not be extracted from the product, because it is produced by a licensed COM component inside the ERP kernel. The sysadmin dependency is therefore stated as a precondition to be checked against each deployment, not as a property that can be assumed of Netsis installations, and the only database privilege configuration this advisory can attest to is the one that was tested
- **Other versions were not tested**, and the Oracle backend the product also supports was not exercised. The 107 routes lacking an `[Authorize]` attribute are an additional unauthenticated surface that should be assumed to contain further instances of the same defect class until audited
- **Identifier status**: at the time of research the product had no publicly disclosed identifiers and no vendor security advisory in the public record; this is original research against an undisclosed attack surface

## Impact

- **Elevation tier**: operating-system command execution on the ERP database host with the identity of the SQL Server service account — `NT AUTHORITY\SYSTEM` in the verified configuration. Command-execution identity is the database service account and is not SYSTEM on every possible SQL Server configuration
- **What SYSTEM on that host means**: control of the ERP database the organization runs on that host, including the product registry store that the vulnerable query itself reads; the ability to tamper with or destroy the financial and accounting data it holds; exfiltration of the entire database; and a pivot position into whatever internal network hosts the ERP database
- **Disclosure tier**: where the service login is not sysadmin, the same unauthenticated request still gives blind read access to the ERP database, which for a financial system is itself a reportable breach of confidentiality
- **Confidentiality / Integrity / Availability**: High / High / High at the elevation tier
- **Verification caveat carried into the severity claim**: the `nt authority\system` identity above was observed on a reconstruction of the product pipeline hosted on loopback, with one IL-patched licensing method, against SQL Server Express — not on a stock installation attacked across a network. Remote reachability over a network follows from the endpoint's construction and from the gateway being published as an integration point; because the reconstruction's listener was bound to loopback, the network exposure itself is a code and deployment argument rather than an observed remote run. The sink, the authentication ordering and the SQL concatenation involved are unmodified product code
- **Detection**: the injection is blind at the HTTP layer, so confirming it requires timing measurement, an observable side effect such as the `xp_cmdshell` state change, or an output-retrieval channel the attacker has separately established — which this research did not demonstrate. Every readback of the marker file in our verification was performed locally by the harness on the target host itself, and no channel for reading it remotely was demonstrated; an attacker who needs the command output rather than its occurrence would have to establish one. Blindness is a detection inconvenience, not a mitigation: it did not prevent command execution in any of the four verification runs against the reconstruction

## Mitigation

1. Parameterize the sink: rewrite `GetIdmUserLastSessionInfo` to bind the registry-name value as a command parameter, never as concatenation, and apply the same review to every other data-access method that builds `CommandText` by concatenating a string argument
2. Move the database call behind the credential check: `GrantResourceOwnerCredentials` must not touch the database with client-controlled input until `OAuthManager.LogIn` has succeeded, and a blank `dbname` combined with a present `idmuserid` should be an invalid request rather than a lookup trigger
3. Least privilege on the service login: connect with a dedicated SQL login holding only what its queries require, not dbo or sysadmin; explicitly deny ALTER SETTINGS and keep `xp_cmdshell` disabled. This removes the operating-system escalation only and must not be presented as a fix for the injection — unauthenticated data disclosure remains
4. Make the blacklist real and apply it on every SQL execution path, including directly constructed commands; treat it as secondary hardening only, since a deny list is inferior to parameterization
5. Default deny at the pipeline: add a global authorization filter, mark the endpoints that must stay anonymous explicitly, audit the 107 routes currently lacking `[Authorize]`, and set `AllowInsecureHttp` to false in production so bearer grants cannot be submitted over cleartext
6. Validate the identity field: apply a length-bounded format whitelist to `idmuserid`, restricted to the character set a legitimate identifier requires, and reject anything else before it reaches the login object
