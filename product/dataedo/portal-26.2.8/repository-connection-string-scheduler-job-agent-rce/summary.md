# Dataedo Portal 26.2.8 with Dataedo Agent 26.2.8 - Unrestricted Job-Type Deserialization in the Agent Scheduler Storage, Reached Through the Repository Connection-String API (CWE-502)

Advisory: https://0day-rubbish.com/blog/dataedo-portal-repository-connection-string-scheduler-job-agent-rce
Repository: https://github.com/Exploit-Garbage/0day-Rubbish
Contact: disclosure@0day-rubbish.com

## Summary

Dataedo is an enterprise data-catalog and data-governance platform from Dataedo sp. z o.o. (Poland). Its Portal component authenticates an administrator-role principal and, on `GET /api/repository/connection-string`, returns the repository database connection string encrypted with `SimpleAES` — an AES-256-CBC construction whose 32-byte key and 16-byte IV are hardcoded byte-array literals in the shipped `Dataedo.Settings.dll`, so anyone holding a copy of the product can decrypt the response offline. The recovered login is a sysadmin-level credential on the repository database, which also contains the Hangfire scheduler storage in the `[Scheduler]` schema. The Dataedo Agent, a separately installed Windows component, polls that schema with two Hangfire server workers and applies no invocation-type restriction: writing one row into `[Scheduler].Job` with an `InvocationData` document naming `System.Diagnostics.Process` / `Start`, plus one row into `[Scheduler].JobQueue`, causes the Agent to execute `cmd.exe` with attacker-chosen arguments on the Agent host. This is a post-authentication chain, not a zero-click anonymous one: the entry route requires role action 11 or above (verified — a zero-permission principal was refused a session with HTTP 400 `ACCESS_WITHOUT_ANY_PERMISSIONS`), and the execution outcome additionally requires a Dataedo Agent attached to a repository database the attacker can reach, which are deployment conditions outside the attacker's control. In the verified shape the command ran as `nt authority\system`.

- **Component**: Portal side — `GetConnectionStringQueryHandler` (`Dataedo.Application:12789`) returning `SimpleAES.GetEncrypted(...)` (`Dataedo.Application:12793`), and `Dataedo.Settings.Cryptography.SimpleAES` (`Dataedo.Settings:64-71`, `:72-77`). Agent side — `AgentServiceRegistration.AddScheduler` and `FilterInitializer`.
- **Sink and source**: sink is Hangfire invocation-type resolution leading to `Process.Start(string, string)` on the Agent host; sources are the authenticated HTTP response body (a 528-digit ciphertext, 176 bytes, 11 AES blocks) and the `[Scheduler].Job` / `[Scheduler].JobQueue` row content, neither of which is validated for what it carries.
- **Sanitization**: none on the execution path. `GlobalJobFilters.Clear()` leaves no filter that inspects the invocation type; the two `IClientFilter` instances run only on the client-side creation path and return early unless the declaring type implements `ISchedulerTaskExecutor`. Sanitization that does exist elsewhere in the product (`SqlConnectionStringBuilder` normalization, `EscapeSql`, parameterized `FromSqlRaw`, RSA-PSS connector signature verification with XSD validation and 31 prohibited keywords) does not touch this path.

## CVSS Score

- **Score**: 8.1 High (CVSS:3.1/AV:N/AC:H/PR:H/UI:N/S:C/C:H/I:H/A:H) - an authenticated repository-management principal recovers sysadmin-level repository credentials and, through the scheduler storage, obtains arbitrary command execution on a different component running on a different host.
- **Attack Vector (AV:N)** — the entry route is a network HTTP API and the injection path is a network database listener; neither requires local access.
- **Attack Complexity (AC:H)** — two conditions beyond the attacker's control must hold: a Dataedo Agent must be attached to that repository database, and the attacker must have a network path to the database listener. Both held in the verified shape; neither is guaranteed by the product.
- **Privileges Required (PR:H)** — only role action 11 or above was demonstrated to reach the disclosure. PR:L is unsupported: a principal with zero application permissions received HTTP 400 and no session.
- **User Interaction (UI:N)** — no victim click, page visit or administrator action on the Agent host participates.
- **Confidentiality / Integrity / Availability (C:H / I:H / A:H)** — arbitrary command execution at the Agent process identity, plus a repository credential that exposes the entire catalog and every stored downstream data-source secret in offline-decryptable form.
- **Scope**: Changed. The vulnerable component is the Portal web application, whose authority ends at its own process and role model; the impacted component is the Dataedo Agent host — a separate installable component, separate process, separate identity, separate machine — reached through a third component (the repository database) whose credentials are themselves the object of the confidentiality failure. Cross-component and cross-host impact is the textbook Scope change.
- **CWE**: CWE-502 (Deserialization of Untrusted Data) primary, with CWE-470 as an equally defensible characterization; contributing CWE-321 (hard-coded cryptographic key), CWE-522 (insufficiently protected credentials), CWE-863 / CWE-284 (incorrect authorization, missing privilege separation), CWE-250 / CWE-732 (execution with unnecessary privileges).
- **Conditional reading, labelled and not the headline**: 9.1 High with CVSS:3.1/AV:N/AC:L/PR:H/UI:N/S:C/C:H/I:H/A:H, applicable only to deployments where a Dataedo Agent is known to be attached to the repository and the repository listener is reachable from the attacker's network position.
- **Rejected reading**: 6.6 Medium with CVSS:3.1/AV:N/AC:H/PR:H/UI:N/S:U/C:H/I:H/A:H, rejected because execution demonstrably occurs on another component and host under another service identity.
- **Score provenance**: every figure above was computed from the vector printed beside it with CVSS 3.1 weights and round-up semantics. An earlier vector built on an anonymous-reachability premise was withdrawn together with the refuted claim; no inherited score is published. No item from the adjacent disclosure group contributed to any figure here.

## Affected Products

- Dataedo Portal 26.2.8, and Dataedo Agent 26.2.8, from Dataedo sp. z o.o. (Poland). Both components are in scope because the chain crosses from one to the other: the Portal discloses the credential, the Agent executes the injected job.
- Affected components: Portal — the repository connection-string query handler and the `SimpleAES` static-key construction in `Dataedo.Settings.dll`; Agent — the Hangfire server registration and filter initialization in `AgentServiceRegistration` / `FilterInitializer`.
- Runtime stack: ASP.NET Core targeting `net9.0` for both components. Portal ships for IIS (ASP.NET Core Module v2 in-process), Linux container (Kestrel) and Windows service shapes; the Agent is `win-x64`-only, installed as a Windows service via `AddWindowsService` with an empty `ServiceConfiguration`. Repository database is Microsoft SQL Server or PostgreSQL; scheduler storage is Hangfire in the `[Scheduler]` schema of that database.
- Only 26.2.8 was executed for both components; no other version or edition is claimed. A newer Portal build, version 26.3.0, obtained during this research (643,279,488 bytes, targeting `net10.0`) reproduced the Portal-side behaviour — same endpoint, ciphertext decryptable with byte-identical key material confirmed by a byte-level search of its `Dataedo.Settings.dll`, 263 migrated tables after anonymous window-state registration — but the Agent binary was **not** re-executed against it, so the execution segment on that build is an argument from the absence of change signals, not a verification.
- Verification method and boundary: the vendor's own binaries were extracted from the vendor installers (Portal installer 622,898,392 bytes, SHA256 prefix `75b601aa...41a4e`; Agent installer SHA256 prefix `38111c21...3973`) by parsing the .NET single-file bundle manifest, then run as a Kestrel-hosted Production instance on a private container network and as a real Windows service executable on Windows Server 2025. The Portal was started from the extracted binaries rather than through the install wizard, so any value the wizard would have randomized (notably the JWT signing key in the adjacent group) was left at its shipped default in our instance; that boundary is stated wherever it matters. Static analysis covered 23 assemblies and roughly 190,000 lines on the Portal side, and about 5,600 decompiled C# files overall. The database listener in the Portal-phase container lab was loopback-bound, so the storage write during that phase was performed from the container host; the Agent phase used a host-local SQL Express instance on port 1433, which is the realistic shape for that hop. The Agent ran as a SYSTEM-privileged scheduled task with `rollForward = Major`, and its listener was bound to `http://[::]:15999` for testing only.
- Privilege ceiling: `nt authority\system` on the Agent host in the SYSTEM-scheduled verification shape, and `<agent-host>\administrator` in a console-launched shape. What was **not** reached and is not claimed: the production Windows service account was not confirmed from the installer's service-registration table (LocalSystem is the convention inferred from the empty `ServiceConfiguration`, listed as unestablished); no domain-controller or domain-administrative outcome was attempted; downstream data sources were not accessed.

## Impact

- Arbitrary operating-system command execution on every Dataedo Agent host attached to the affected repository database, at the identity of the Agent process — machine-level authority in the observed shape.
- The Agent host holds, in ciphertext recoverable offline with the same static key, the `credentials` and `ssh_configurations` entries for every downstream data source in the catalog plus SSH tunnel secrets. One compromised Agent host therefore yields plaintext credentials into the estate's data platform without a second vulnerability.
- The recovered repository credential is a sysadmin-level principal over the database that is the product's sole trust anchor: users, licenses, permissions, single-sign-on configuration, login-method switches, one-time login codes, sessions, the public-API switches and the entire catalog. Full confidentiality loss and full integrity loss over the governance record follow from it.
- Persistence is available in two independent forms — the Windows service itself, and further scheduler rows that survive Agent restarts and need only another database write to re-trigger.
- Availability: the same write access halts imports, data-quality runs, exports, classification and profiling refresh by consuming or corrupting their scheduler rows, on a product whose purpose is keeping that pipeline current.
- Lateral movement: the Agent is by design permitted to reach every catalogued data source, so from an Agent host with SYSTEM authority and those credentials the path into warehouse and analytical systems requires no further weakness.
- Detection caveat: the Portal-side step is a single authorized, successful HTTP GET that looks entirely ordinary in access logs, and the decisive event is a database insert into a schema the Portal itself writes during normal operation. Discriminating signals are specific — an `InvocationData` type outside the vendor's scheduler namespace, a `State.Result` of "Can not serialize the return value", single-digit-millisecond durations, shell binaries in `Arguments` — and none of them are alerted on by the product.
- Deployment caveat: with no Agent attached, the injected row is never fetched and nothing executes. That precondition is real, is outside the attacker's control, and is the reason Attack Complexity is High rather than Low.

## Mitigation

1. **Constrain the invocation type at execution time (the sink fix).** Register a custom Hangfire `ITypeResolver` on both Agent servers that resolves only the vendor's own scheduler job types implementing `ISchedulerTaskExecutor`, and add a server-side filter that transitions any job whose declaring type is not on that allowlist into a failed state before execution. Replace `GlobalJobFilters.Clear()` with a cleared-then-restricted filter set, validate the `InvocationData` shape explicitly, and reject the `System.*` namespace with `System.Diagnostics.Process` as a named test case.
2. **Stop returning the connection string to clients.** Return host and catalog at most, mask the login, and never transmit the password. No transport encryption keyed by material the client already possesses protects the secret.
3. **Replace the static `SimpleAES` key and IV with per-installation key material** — DPAPI on Windows, a managed key service elsewhere, or an installer-generated random key stored outside the assembly. Make the existing `GenerateEncryptionKey()` an actual code path, refuse to start when the factory key is still in use, rotate on upgrade, and move to authenticated encryption (AES-GCM) without a fixed IV; a fixed key with a fixed IV in CBC mode is deterministic and leaks plaintext equality.
4. **Separate catalog administration from scheduler write authority.** The credential read by an administrator workflow must not be able to insert into `[Scheduler]`, and the Agent's credential should be scoped to the scheduler schema. Better still, make job dispatch non-reflective: store a job-type identifier from a closed enumeration resolved through a factory, so storage content selects a behaviour instead of naming a type.
5. **Run the Agent service under a dedicated least-privilege account** and record the chosen identity explicitly in the installer instead of relying on the empty `ServiceConfiguration` default. Isolate Agent hosts and restrict their egress to catalogued data sources.
6. **Close the anonymous repository-management surface** (adjacent group): put the 18 ungated routes behind authentication plus a short-lived single-use setup token issued by the installer; narrow the middleware `ignoredUrls` allowlist so it applies only while the repository is genuinely unconfigured; make the registration state machine single-directional; add a global fallback authorization policy so a missing `[Authorize]` fails closed. Fix `connect-and-upgrade` so it cannot catch `RepositoryAlreadyConfiguredException` and continue into a path that rewrites `WEB_CATALOG_URL` and triggers a schema upgrade.
7. **Pin CORS and harden the JWT scheme** (adjacent group): replace `SetIsOriginAllowed(_ => true)` with a configured origin allowlist and keep `AllowCredentials` only for those origins; set the session cookie to `SameSite=Lax`; refuse to start with the factory `TokensKey`; enable `ValidateIssuer`, `ValidateAudience` and `RequireHttpsMetadata`.
8. **Add regression tests for both halves**: a stored job row whose `InvocationData.Type` is `System.Diagnostics.Process` must never execute and must record an allowlist failure with no child process created; an unauthenticated `POST` to every repository-management route must return 401 in every product state except the token-bearing setup window. Gate both OpenAPI documents behind an environment check or authentication and suppress stack traces in error responses.
9. **Operator measures until a patch exists**: restrict network access to the repository database listener to Portal and Agent hosts only; enable database auditing on `[Scheduler].Job` and `[Scheduler].JobQueue` inserts and alert on the discriminating signals above; complete first-run repository configuration immediately after installation and never expose an unconfigured Portal to an untrusted network; monitor `appsettings.json` on Portal hosts and `configuration[WEB_CATALOG_URL]` for change; rotate the repository credential and treat all prior copies as exposed; treat installer-produced `Dataedo-Web-backup-*.zip` artifacts as credential material; strip reflected `Access-Control-Allow-Origin` headers at the reverse proxy; rotate `JwtAuthentication.TokensKey` if the deployment did not pass through the installer's API-configuration step.

### Adjacent disclosure group (published within this advisory, scored separately, excluded from the CVSS above)

These items are real and reportable, were established during the same work, and are deliberately **not** folded into the RCE vector or its score. They are published inside this advisory rather than as separate advisories because each lacks a complete independent artifact set of its own — no separate published tool and no independent end-to-end verification package each.

- **Unauthenticated repository-management surface (CWE-306, CWE-284)** — 18 ungated routes on `RepositoryController` and its PostgreSQL family, a 17-entry `RepositoryCompatibilityMiddleware.ignoredUrls` allowlist, and no global fallback policy (source-wide searches for `FallbackPolicy`, `AuthorizeFilter` and `RequireAuthenticatedUser` return zero hits). In a deployment window — installer finished but repository wizard pending, container quickstart with an empty catalog, or a repository outage or migration period — an unauthenticated party can register its own repository database; the Portal migrates its full schema there (255 tables on 26.2.8, 263 on the newer build) and persists the switch into `appsettings.json`. Because the login validator checks supplied credentials against the repository database (`SELECT TOP(1) 1 FROM [version]`), the attacker's own SQL login validates, the user is auto-registered through the license path, and the empty sessions table makes `IsFirstWebCatalogUser` true, so `AssignAllRolesToUser` yields full administrator takeover. Demonstrated three times, including a window deliberately re-created by emptying the catalog configuration and restarting the process, and once on the newer build. A healthy configured instance answers HTTP 409, so the exposure is window-shaped. Status: dynamically demonstrated in window states; not demonstrated against a healthy configured instance, which is reported as such.
- **Permanent anonymous tamper, SSRF and information disclosure (CWE-306, CWE-918, CWE-200, CWE-209)** — `POST /api/repository/connect-and-upgrade` returns HTTP 202 on a running instance at any time and rewrites `configuration[WEB_CATALOG_URL]` in the live repository (verified as `http://attacker.example/`), hijacking SAML assertion-consumer redirects, e-mailed links and the front-end base URL persistently, and can also trigger a schema upgrade on a version-lagged instance. Alongside it: outbound TDS connections to an attacker-named host through `available-databases` (94-byte pre-login packet observed at the listener, implying internal port discovery and NetNTLMv2 exposure on Windows deployments); SSRF through `/api/text-editor/link?url=` reaching internal services, the Portal's own Kestrel port (so the internal OpenAPI UI is reachable through that route alone) and the cloud instance metadata endpoint; HTTP 500 with a full stack trace from `database-update-log`; service-account leakage from `identity` on Windows; a deployment fingerprint from `host-environment`; a static `lastOperation` field usable as an anonymous error oracle; both OpenAPI documents served without an environment gate; and an anonymous registration endpoint without rate limiting. Status: dynamically demonstrated for the tamper, the SSRF, the outbound connection and the information leaks.
- **Permissive CORS with credentials (CWE-942, CWE-346)** — `SetIsOriginAllowed(_ => true)` with `AllowAnyHeader`, `AllowCredentials` and methods GET, POST, PUT, PATCH, DELETE, plus a session cookie configured `SameSite=None`. Any website can issue credentialed cross-origin requests and read responses across the cookie-authenticated `/api/*` surface for a logged-in administrator, enabling bulk metadata, credential-configuration and user-list exfiltration plus cross-site state changes on a healthy production instance with no other weakness involved. Status: established by reversing the shipped configuration code; no browser-driven cross-site demonstration was performed, and none is claimed.
- **Factory JWT signing key with issuer and audience validation disabled (CWE-798, CWE-347)** — `TokensKey` is a shipped GUID used as ASCII bytes for HMAC-SHA256, with `ValidateIssuer = false`, `ValidateAudience = false` and `RequireHttpsMetadata = false`, so signature validity is the only protection. Scope is narrower than it first appears: a `ForwardDefaultSelector` confines the JWT scheme to `/public/v1`, leaving `/api/*` on cookie or PAT authentication. Demonstrated in the default-key shape — a forged HS256 token moved `GET /public/v1/custom-fields` from HTTP 401 to HTTP 200 with real catalog data, and the accompanying stack trace placed the token-validation database comparison after signature verification. Boundary: the Windows installer writes a fresh GUID during its API-configuration step, so this applies to container deployments, manual or copy-based deployments, and upgrades preserving an older configuration file; survival in a specific marketplace template was not established and is not claimed. Status: dynamically demonstrated in the default-key shape only.
