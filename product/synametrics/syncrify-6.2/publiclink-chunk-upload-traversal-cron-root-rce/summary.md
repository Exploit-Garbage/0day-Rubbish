# Synametrics Syncrify 6.2 build 1178 - Path Traversal in the PublicLink Chunk-Upload Branch (CWE-22) Leading to Root Command Execution

Advisory: https://0day-rubbish.com/blog/synametrics-syncrify-publiclink-chunk-upload-traversal-cron-root-rce
Repository: https://github.com/Exploit-Garbage/0day-Rubbish
Contact: disclosure@0day-rubbish.com

## Summary

Synametrics Syncrify 6.2 build 1178 is a closed-source incremental backup and file-replication server from Synametrics Technologies, Inc. (United States), written in Java and served by an embedded Tomcat 9.0.113 through the vendor's in-house `sradef` framework, whose single front controller routes every request as `/app?operation=<op>&st=<step>` to a handler registered in `WorkerMappings.xml`. The `PublicLink` handler (`operation=pb`) implements the server's PublicLink client protocol; its chunked-upload branch, selected by `st=u`, reads a length-prefixed binary frame from the request body and hands one field of that frame straight to a file constructor. In `PublicLink.java:70-110` the decompiled method reads four big-endian integers and one length-prefixed UTF-8 string, then evaluates `new File(base, filename)` with no rejection of `..`, no rejection of path separators, no basename extraction and no canonical containment check, creates any missing parent directory with `mkdirs()`, and opens the result in append mode. The consequence is an arbitrary file write: a chunk named `../../../../../etc/cron.d/evilcron` leaves the per-user PublicLinks folder `/opt/Syncrify/PublicLinks/<user>/<generated-folder>/` and lands a cron fragment, and because the server process holds uid 0 in the documented Linux deployment shape and a cron daemon was active, that fragment is executed by the scheduler as root. We verified the chain end to end; the identity capture the cron job produced was `uid=0(root) gid=0(root) groups=0(root)`.

The principal is the interesting part. This is not an administrator path. The gate on `operation=pb` is a `secLevel=0` registration in `WorkerMappings.xml`, so the framework itself demands no administrator session; the only decision is the handler's own authentication call, which validates a credential from the **backup-user** store (`config/UserMappings.xml`, `syncrify.users.DefaultUserManager`) and not from the web-administrator store (`config/umap.dat`, `sradef.config.SecurityManager`). Those two stores are independent and must not be conflated: a backup user is a low-trust account whose entire legitimate job is to move bytes into its own repository. A low-trust uploader reaching a root-executed scheduler directory is a privilege-boundary failure inside the product, not a misconfiguration of the host.

- **Component**: `PublicLink` handler, `operation=pb`, chunked-upload branch `st=u` (`st=u` -> `f()` at `PublicLink.java:127` -> `int E()` at `PublicLink.java:70-110`), served by the front controller on the main web listener of the embedded Tomcat 9.0.113.
- **Sink**: `new File(E(), filename)` followed by `mkdirs()` and an append-mode `FileOutputStream`; the path base is the authenticated user's own PublicLinks folder, the filename is attacker-supplied, and nothing constrains it.
- **Source**: the `filename` field of the in-house binary chunk frame in the request body, framed as `[int32 protocol][int32 chunkNumber][int32 totalChunks][int32 size][int32 nameLength][UTF-8 name][size bytes]`, big-endian, read from `request.getInputStream()`.
- **Sanitization**: none on this branch. The same tree demonstrably contains three working traversal defenses - a separator check (`indexOf(47)`, `indexOf(92)`) in the profile-upload, profile-fetch and file-splitter handlers, a `getName()` collapse in the multipart upload path, and an `indexOf("..")` check in the download path - none of which this branch calls. That asymmetry is what makes this an oversight rather than a design decision.

## Affected Products

- **Product**: Syncrify, incremental backup and file-replication server (rsync-over-HTTP client protocol plus PublicLink sharing plus a web administration portal)
- **Version analysed**: 6.2 build 1178, `SyncrifyServer.jar` from the distributed Linux tarball archive
- **Vendor**: Synametrics Technologies, Inc. (United States)
- **Component**: the `PublicLink` handler's chunked-upload branch, `operation=pb&st=u`, inside the `sradef` front controller (`com.synametrics.sradef.servlet.FrontController`)
- **Runtime stack**: Java on an embedded Tomcat 9.0.113 launched by `com.synametrics.sradef.BootLoader` (`jre/bin/java -server -Xmx512m -cp lib/*.jar`), in-house `sradef` framework, bundled JRE; an embedded database is configured but disabled (`rdbmsEnabled=false`) and was not listening
- **Shared-framework note**: the same in-house `sradef` web framework also underpins the vendor's sibling products Xeams and SynaMan; the shipped `web.xml` of this build still carries `display-name` `SynaMan`, and the shared `lib4njre.jar` supplies `com.synametrics.commons.util.*` to all of them. We say this because it tells the vendor where else to audit the same construction. **This advisory makes no claim about any product other than Syncrify 6.2 build 1178**, and no sibling product was tested here.
- **Scope of the affected-version statement**: 6.2 build 1178 is the only version whose code we decompiled and against which we ran the chain. Other versions and editions were not enumerated, no cross-version comparison was performed, and no other version is claimed. The construction is simple enough that adjacent versions very likely share it, but we have not established that, so we do not assert it.
- **Verification method and its boundary**: static reversal of the decompiled handler tree, then a live run against a deployed instance installed from the distributed archive into `/opt/Syncrify` and started with `./run.sh`. Two properties of that instance were ours rather than the product's, and both are carried through the advisory as boundaries: the portal listener was bound to loopback by an explicit configuration edit we made before testing so the host was not reachable from outside, and the backup-user store did not exist after installation, so the account used for verification was written into that store by hand with plaintext password comparison rather than provisioned through the administrator's user-management operation, which is additionally licence-gated.
- **Privilege ceiling**: root on the server host was reached and is claimed - `uid=0(root) gid=0(root) groups=0(root)`. What was **not** reached: unauthenticated access to this sink. No path from an anonymous request to this write was found, and the credential gate on the backup-user protocol held up under examination.

## Impact

- **Arbitrary file write, attacker-chosen path and attacker-chosen bytes**: the chunk branch writes exactly the `size` bytes it reads from the request body to whatever absolute path the chunk name resolves to, in append mode, creating missing parent directories on the way. The `/etc/cron.d` destination is the escalation path we demonstrated, not the limit of the primitive.
- **Command execution as uid 0**: the written fragment is evaluated by the host cron daemon as a root-authored job definition, so the command runs with the full authority of the process identity the server already holds. In the verified deployment shape the server runs as root and cron is active.
- **Every stored backup is exposed**: this is backup infrastructure. Root on the server means read access to the whole repository tree - customer filesystems, home directories, database dumps, source trees, whatever is being backed up - plus the server's own configuration, which holds administrator and user credential material and transport secrets.
- **Privilege boundary crossed inside the product**: the principal that achieves this is a backup user, the lowest-trust account type the product has, created by an administrator for the purpose of uploading bytes into one repository. Nothing about that role is supposed to reach a host-scheduler directory.
- **Persistence by construction**: a cron fragment runs on every minute boundary until someone deletes it, so a single successful chunk write gives recurring execution rather than one shell. The proof-of-concept ships a `--cleanup` flag that removes exactly the two paths it created.
- **Availability**: as root the attacker can stop the backup service, corrupt or delete repositories, tamper with retention and version data, or use the host's own package and service tooling - all of which also destroys the recoverability that is the entire reason the product exists.
- **Detection caveat**: nothing about the successful write is visible to the application. The upload branch returns its normal acceptance reply (`code="1"`, `<payload>0</payload>`) and logs no path-decision failure, because from the handler's point of view the upload succeeded. Detection has to come from outside the application - filesystem integrity monitoring on `/etc/cron.d`, or noticing chunk-upload requests whose `Content-Type` is `application/octet-stream` with a small body from a client that is not performing a real backup.
- **Append-mode detail worth knowing for defence**: because the writer appends, a repeated request does not replace the fragment, it adds lines to it. A malformed second line does not undo a valid first one, so a defender cannot rely on an attacker needing to get the fragment byte-exact in a single shot.

## PoC

`exploit/synametrics_syncrify_publiclink_chunk_upload_traversal_cron_root_rce.py` - Python 3 standard library only, no third-party dependency, no hardcoded target. `--host` defaults to `127.0.0.1` and `--port` to `5800`; the backup-user credential pair is mandatory and has no default; the command, marker path, fragment path, traversal depth, wait, schedule and user field are all arguments. It authenticates through the PublicLink handler, captures the session identifier, frames one chunk according to the documented binary layout, posts it to `st=u`, waits for the scheduler and reads back the identity capture. `--control` performs the identical authenticated upload with a non-traversing chunk name and then asserts that nothing appeared in the cron directory, which is the negative control that isolates the traversal. `--cleanup` removes only the two paths the script created. The default payload is an `id` capture into a marker file; nothing destructive is performed and no product file is overwritten or deleted.

## Mitigation

1. **Constrain the chunk name at the sink.** In the `st=u` upload branch, reject any `filename` containing `/`, `\` or `..` before it reaches the file constructor, and reduce it to a single path component. The tree already has the working pattern for this: the profile-upload, profile-fetch and file-splitter handlers reject separators with `indexOf(47)` and `indexOf(92)`, and the multipart upload path passes the name through `getName()`. Factor one helper and call it from every handler that builds a path from client input, so the four upload families cannot diverge again.
2. **Add a canonical containment check after construction, not instead of it.** Resolve the intended target with `getCanonicalPath()` and require that it starts with the canonical path of the authenticated user's own PublicLinks folder followed by a separator. Name-based rejection alone will be defeated by encodings or absolute names; containment is the property that actually matters, and it also closes an absolute chunk name.
3. **Stop creating whatever directory the client names.** The `mkdirs()` call on the resolved target's parent means a client can materialise directory structure anywhere the service identity can write. Create the destination directory once, from server-side state, and refuse the request if the resolved target is not already inside it.
4. **Do not run the service as root.** Drop to a dedicated unprivileged account, and grant that account write access only to the repository and PublicLinks subtrees. This alone removes the escalation from arbitrary file write to root command execution, because a non-root process cannot place a usable fragment in `/etc/cron.d`; it does not remove the file write itself, so it is defence in depth and not a fix.
5. **Give the protocol a real chunk-placement contract.** In the decompiled listing, `chunkNumber` and `totalChunks` are read from the frame and then not used to bound or place the write - the stream simply appends. Reassembly should be server-controlled: allocate the destination from session state, verify the frame sequence, and write into a staging area outside any scheduler-, service- or script-consumed directory before moving the file into place.
6. **Audit the sibling handlers in the same framework family.** The same `sradef` front controller, the same per-handler `secLevel` model and the same `lib4njre.jar` helper library are shared with the vendor's other products; the shipped `web.xml` of this build still carries `display-name` `SynaMan`. Every construction in this framework that builds a filesystem path from a client-supplied field deserves the same containment review, in this product and in the others. This advisory makes no claim about those products - we did not test them - and the point is only that the root cause is framework-shaped rather than handler-local.
7. **Close the container-level gap that makes per-handler levels the only gate.** The shipped `web.xml` security constraint covers only `DELETE`, `OPTIONS` and `PUT`; its own load message says every other method is uncovered. Requests arriving over `GET` and `POST` therefore depend entirely on each handler declaring a correct `secLevel`, and a handler registered at level 0 with its own internal authentication is one decision deep. A defence-in-depth constraint over the whole application, with handler-level exemptions as exceptions rather than as the rule, would make a missing level non-fatal.
8. **Add a regression test that fails the release.** Post a chunk whose name is `../../../../etc/cron.d/x` (and variants: an absolute name, a URL-encoded name, a name with a trailing separator, a name whose `..` segments exceed the repository depth) through an authenticated backup-user session against a throwaway instance, and assert both that the reply is a rejection and that no file appeared outside the repository subtree. A test at this level catches the whole class, not just this instance.
9. **Operator-side measures until a patch exists.** Restrict who can obtain a backup-user credential, because each one is a potential root write; place the portal listener on a management network or behind an authenticating reverse proxy and do not expose it to the internet; run the service under a dedicated unprivileged account; enable filesystem integrity monitoring on `/etc/cron.d`, `/etc/crontab`, `/var/spool/cron`, the init system's unit directory and the repository tree, alerting on any new file whose content matches a cron job line; and review the PublicLinks folder tree for files whose names or locations do not correspond to shared content.
