# StreamSets Transformer 3.17.0 — "none" Authentication Mode Fallback + Un-sandboxed ScalaDTransform Code Execution → Anonymous Root RCE

Advisory: https://0day-rubbish.com/blog/streamsets-transformer-auth-none-scaladtransform-code-execution
Repository: https://github.com/Exploit-Garbage/0day-Rubbish
Contact: disclosure@0day-rubbish.com

## Summary

StreamSets Transformer 3.17.0, the Spark-engine data-pipeline and ETL platform from StreamSets Inc. (subsequently acquired by IBM), fails open on its web-tier authentication setting and ships an un-sandboxed code-execution stage behind it. Two independent defects combine into anonymous remote code execution as root:

- **Missing authentication from an insecure code-level default (CWE-306 / CWE-1188).** `WebServerTask` declares `AUTHENTICATION_DEFAULT = "none"`, and `createSecurityHandler()` returns `null` for that mode, so Jetty installs no authentication handler at all. The same state additionally triggers `WebServerModule.provideNoAuthenticationRoles`, which registers `AlwaysAllRolesFilter` on `/*` whenever the mode is `none` and DPM is disabled (`dpm.enabled=false`, the recorded default). That filter makes `isUserInRole()` return `true` for every role and `getUserPrincipal()` return a synthesised `admin`, so every `@RolesAllowed` check passes (CWE-285).
- **Un-sandboxed code injection (CWE-94).** The `ScalaDTransform` processor in `streamsets-spark-basic-lib` exposes a `ConfigDef.Type.TEXT` field named `code`. It is passed to `ScalaTransform`, compiled by `TransformScriptRunner` using the full Scala compiler `scala.tools.nsc.Global`, and executed through `runner.run(dataFrames)` inside the Transformer JVM. The research record names exactly three absences on that path — no `SecurityManager`, no sandbox and no API allowlist — and no further absence is asserted here. Positively, the compiled stage runs in the service's own JVM under the container's own operating-system identity, which is uid 0, and `scala.sys.process` is on the classpath, so the compiled stage spawns OS processes via `ProcessBuilder`.
- **The chain.** Five anonymous operations over `/rest/v1/` on port 19630 — create a pipeline (`PUT ...?autoGeneratePipelineId=true`, HTTP 201), fetch its skeleton (`GET`, 200), save a three-stage graph carrying the Scala payload (`POST ...?rev=0`, 200), start it (`POST .../start`, 200), and poll its status to `FINISHED`. The final operation is a poll and the recorded run polled six times, so those five operations were ten HTTP requests in total. The only non-optional header is `X-Requested-By: SDC`, a fixed CSRF constant — not a credential. The container process is uid 0, so the first command already runs as root.
- **Verification.** End-to-end against a live instance of the official image, over plain HTTP, three independent runs with per-run unique marker files: `id` returned `uid=0(root) gid=0(root) groups=0(root),1(bin),2(daemon),3(sys),4(adm),6(disk),10(wheel),...` `sh -c` semantics are established by the exploit wrapper itself rather than by any single run: the wrapper is recorded as `"%s > %s 2>&1; echo POCOK >> %s"`, so it always carries an output redirect, a stderr merge and a `;` separator, and every marker file demonstrably contains the appended `POCOK` line that only the post-`;` half could have written. A third run, whose command the record labels `whoami; hostname`, produced a different marker — but the record's stated command and its recorded marker content are mutually inconsistent, since 23 bytes matches `ARBITRARY_CMD_OK` plus `POCOK` and not the output of `whoami; hostname`. No argument is built on that run, and the inconsistency is disclosed in the analysis rather than resolved by adopting one side. Command output is recovered out of band from the container filesystem; it is not returned over HTTP. The shipped PoC is `exploit/streamsets_transformer_auth_none_scaladtransform_rce.py`, standard library only, with `--mode probe` to test the precondition without attacking; it is a parameterised re-implementation of the chain and is not the research-phase client that produced the recorded transcripts.
- **The honest qualification, and it is load-bearing.** `none` is **not** what the distributed image ships. The shipped `/etc/transformer/transformer.properties` sets `http.authentication=aster` at line 85, and documents `none` as a valid value in the comment at line 83; a stock container is therefore not anonymous. `none` is reached by explicit operator choice, or by loss or overriding of that property, which makes the code fallback apply. The instance used for verification was deliberately configured this way. This advisory classifies the finding as configuration-dependent with an insecure fail-open default, and scores both readings rather than claiming a factory-default anonymous compromise.

## CVSS Score

- **Primary (as distributed — configuration-dependent):** 8.1 High — `CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H`. `AC:H` because success depends on a target state the attacker does not control: the effective authentication mode must resolve to `none`, which the shipped properties file does not set.
- **Conditional (deployments whose effective mode is `none`, including the verified instance):** 9.8 Critical — `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`. No preconditions remain in that state and the chain completed deterministically in three of three runs.
- **Derivation.** The research record for this finding carries no vector and no score; both values above are this advisory's own derivation, metric by metric, with scope kept Unchanged because the code executes inside the same JVM and container authority that accepted the request. The source record's CWE-306 and CWE-94 are carried unchanged; CWE-1188, CWE-285 and CWE-250 are added by this advisory.

## Affected Products

- **Vendor:** StreamSets Inc. (subsequently acquired by IBM)
- **Product:** StreamSets Transformer — the Spark-engine sibling of StreamSets Data Collector, which uses a different engine and a different code stage
- **Version verified:** 3.17.0, analysed from the official container image `streamsets/transformer:3.17.0`; stack recorded as Java 8, Jetty 9.4.22, Jersey, Guice, Spark with Scala 2.11
- **Other versions:** 3.x releases sharing the same `WebServerTask` fallback and the same `ScalaDTransform` stage are likely affected, but no other release was installed, decompiled or probed
- **Precondition:** effective `http.authentication` resolving to `none` — by operator choice, by property loss falling back to the code default, or by deliberate selection to bypass `aster` mode's DPM registration requirement — together with DPM disabled
- **Runtime context:** the verified container ran as uid 0 and published port 19630; no reverse proxy, WAF or mutual TLS stood in front of it in the recorded deployment

## Impact

- **Anonymous root code execution** in the verified configuration: no credentials, no session, no user interaction, no MITM position, no privilege-escalation step. The compiled Scala runs inside the uid 0 container JVM.
- **Confidentiality High:** unrestricted read of every stored pipeline definition (including connection configuration and any credentials held in it), of `/etc/transformer/*.properties`, of the JVM environment and of the whole container filesystem.
- **Integrity High:** unrestricted modification of product configuration, stored pipelines and container files. Because pipeline definitions persist, an attacker can leave a dormant stage that re-executes on a later run — an inference from observed persistence, not tested.
- **Availability High:** the service, its Spark runs and the container can be stopped, corrupted or driven to exhaust host resources; as a pipeline engine between upstream sources and downstream warehouses, its loss interrupts data flows beyond the host.
- **No sandbox was bypassed, because none exists.** The research record names exactly three absences on the compile-and-run path — a `SecurityManager`, a sandbox and an API allowlist — so containerisation is the only isolation between an anonymous HTTP request and root command execution. No further absence is asserted: no check applied to the emitted bytecode, no limit on how the compiled class is loaded, and no use of a distinct lower-privilege process for compilation were examined here, and none of the three is claimed as a recorded absence. Recorded separately, as an observation rather than as an absence, is that the Scala executes in the service's own JVM under the container's uid 0 identity.
- **Detection is hard.** Every request in the chain is an ordinary permitted operation — create, save, start. The distinguishing signal is the content of a `code` field on a stage type the product ships and documents. What the product logs for these operations was not examined, so no claim is made about log visibility.
- **Independence from prior research.** StreamSets Data Collector has been the subject of earlier research, including this repository's own advisory on hard-coded credentials reaching `ShellDExecutor` plus a sudoers escalation from the unprivileged `sdc` user (uid 20159). That is a different product, a different engine, a different stage family and a different broken assumption; nothing published about it covers this chain, and our record's prior-art survey found no published vulnerability entries for Transformer at all. No CVE identifier is asserted here.

## Mitigation

- **Vendor — fail closed:** replace the `"none"` fallback literal in `conf.get(AUTHENTICATION_KEY, "none")` so that an absent or unparseable `http.authentication` refuses startup instead of starting an open listener.
- **Vendor — restrict `none`:** require an explicit acknowledgement property to select it, banner it in the UI and logs, and make the anonymous surface read-only so `PUT` create, `POST` save and `POST` start return 403 rather than 201/200.
- **Vendor — remove `AlwaysAllRolesFilter`:** when no security handler is installed, `@RolesAllowed` endpoints should default-deny, and any synthesised principal should be a named low-privilege role that no pipeline-authoring endpoint accepts.
- **Vendor — sandbox or drop the Scala stage:** restrict stage execution with a `SecurityManager` or a package-allowlist `ClassLoader`, block `scala.sys.process` / `java.lang.Runtime` / `java.lang.ProcessBuilder`, prefer pre-compiled signed stage libraries over inline source, and stop shipping the container as uid 0 (the sibling Data Collector image already runs as `sdc`, uid 20159).
- **Operator — verify and pin:** test every instance with an unauthenticated `GET /rest/v1/pipelines` (200 means it is anonymous right now), pin `http.authentication` in `transformer.properties`, alert on drift, and never let the key be silently absent — absence resolves to `none`.
- **Operator — contain:** keep port 19630 off untrusted networks (VPN, mutual-TLS mesh or an authentating reverse proxy), run the container with `--user`, a read-only root filesystem, `--cap-drop=ALL` and no host mounts, treat pipeline-write permission as code-execution capability, and alert on new `com_streamsets_pipeline_spark_transform_scala_ScalaDTransform` stages in previously Scala-free pipelines.
